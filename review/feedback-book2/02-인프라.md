# 피드백 — 공공/IoT SRE 리드 (가상 2권 베타) / 인프라

날짜: 2026-05-18

> NCP / NKS 운영 5년 + 한전 AMI / 세종형 IoT 게이트웨이 운영 3년 시각으로 읽었다.
> 2권의 정체성 — "25명 / 공공 / 시계열" — 은 1권보다 훨씬 도전적인 영역이다. 책의 톤은 좋다.
> 다만 "NCP 단일 / 인프라 3명 / 5분 안전 SLA / IoT 0.1% 손실률" 이 동시에 성립하느냐를 솔직히 짚는다.
> 1권 베타 리뷰가 "쿠팡/네이버 출신 SRE" 톤이었다면, 본 리뷰는 **공공 SI + 스마트시티 운영자 톤**이다.

## 1. 사실 / 정확성 (A)

| 위치 (파일:절) | 발견 | 제안 |
|---------------|------|------|
| case §11.1 / 02장 §1.2 — "NCP 단일 클라우드" | NCP 의 매니지드 서비스 폭이 본문에서 "보통" 으로만 표시되고 1권의 AWS 와의 **격차 표** 가 없다. 25명 조직이 NCP 단일로 가면 다음 격차가 실제 작업으로 떨어진다 (2026 상반기 시점, 확인 필요): (a) **TimescaleDB 매니지드 없음** — Cloud DB for PostgreSQL 에 extension 설치는 가능하나 hypertable 의 background worker / continuous aggregate / chunk 압축 정책은 self-tune. 사실상 self-host PostgreSQL on VM 또는 NKS 운영에 가깝다. (b) **ClickHouse 매니지드 없음** — Altinity Cloud / ClickHouse Cloud 가 NCP 한국 리전에 없음. NKS self-host 또는 ClickHouse Cloud (AWS 리전) 외부 호출. case §11.2.2 의 "ClickHouse (NCP)" 는 사실 확인 필요. (c) **CDSS (Cloud Data Streaming Service) 는 MSK 호환이지만 Kafka Connect / Schema Registry 매니지드가 약함** — IoT ingester 에서 Avro / Protobuf schema evolution 운영 시 self-host Confluent Schema Registry 필요. (d) **NCP Managed Redis 의 클러스터 모드 제약** — ElastiCache 대비 데이터 마이그레이션 / online resharding 도구 부족. (e) **Secret Manager 의 동적 시크릿 (DB 동적 자격증명) 없음** — Vault dynamic secrets 같은 기능 부재. 결과: 25명 조직이 NCP 단일을 택하면 **운영 부담이 1권 대비 1.5~2배** 일 수 있다. | 02장 §1.2 또는 신규 §1.3 에 "NCP 의 AWS 매니지드 격차 표" 추가. 영역별 (DB / 스트리밍 / 관측성 / 보안) 격차를 명시. case §11 의 "ClickHouse (NCP)" 는 "ClickHouse on NKS self-host" 또는 "ClickHouse Cloud (외부 리전)" 로 정정 — 둘 중 어느 쪽인지가 인프라 부담 / 데이터 주권에 직접 영향. |
| case §11.1 / 02장 §2 — "NKS 클러스터 + 서비스 약 12개" | NKS 의 실제 운영 격차 (EKS 대비) 가 본문에서 안 다뤄짐 — (a) **NKS 의 컨트롤 플레인 가용성 SLA 가 EKS (99.95%) 와 같은지 사실 확인 필요**, (b) **NKS Auto Scaling 의 노드 그룹 mixed instance / spot 지원이 EKS 만큼 성숙하지 않음** — IoT 폭주 시 노드 확장 lag 가 EKS 대비 큼, (c) **NCP IAM ↔ Kubernetes RBAC 통합 (IRSA 등가)** — NCP 의 Sub Account ↔ ServiceAccount 매핑 도구가 EKS Pod Identity / IRSA 만큼 깔끔하지 않음. 25명 조직이 NKS 12 워크로드 + IoT 폭주 노드 자동확장 + ArgoCD self-host + Nginx Ingress + Helm 운영을 3명으로 한다는 게 본문 톤은 "당연히 가능" 인데, 실제론 **인프라 3명 중 0.7~1.0 명이 풀타임 NKS 전담** 으로 빠진다. | (a) NKS vs EKS 격차 표 추가 (컨트롤 플레인 SLA / 노드 그룹 / IAM 통합 / 업그레이드 주기). (b) 02장 §2.2 의 "Managed PaaS 도 가능하지만 IoT 의 stateful 특성과 도메인팀 자율을 위해 NKS 채택" 은 **너무 가볍다** — 25명에서 도메인팀 자율은 환상이고, IoT 만 NKS, 나머지는 Container Registry + VM + Cloud Functions 의 혼합도 동등 옵션으로 비교해야 한다. |
| case §6 / 02장 §5.1 — "취약계층 안전 알람 99.99% / 5분 이내" | **이 책 전체의 핵심 SLA** 인데, 5분의 분해가 본문에 없다. 실제 5분 안에 사회복지사에게 "도달" 의 정의가 (a) FCM/APNs 전송 ACK 까지인지, (b) 사회복지사가 알림을 본 시점인지, (c) 사회복지사가 "확인" 버튼을 눌러 회신한 시점인지에 따라 99.99% 의 의미가 완전히 다르다. (a) 라면 알림 인프라만 책임, (b) 라면 사회복지사 핸드폰 / 통신사 / 푸시 전달 chain 까지 책임, (c) 라면 사회복지사의 근무 상태까지 SLA 안에 포함. 99.99% = 월 4.32분 다운 — **사회복지사 한 명이 회의 / 운전 / 식사 중이라 5분 안에 못 보면** 도달률 깨짐. 인프라가 아무리 다중화해도 사람 chain 에서 깨진다. | (a) "도달" 의 정의를 본문에 명시 (제안: "다중 채널 중 1개 이상 ACK 까지"). (b) 사회복지사 "회신" 까지 포함하는 별도 SLO (예: 회신 15분 이내 95%) 를 분리. (c) "인프라 SLA (전송 ACK) 99.99% + 운영 SLA (회신) 95% / 15분" 의 2단 구조로 분리. |
| case §11.1 + §8 — "알람 처리기 다중화 (앱 푸시 → SMS → 자동 전화)" | 다중화의 실제 도달률이 본문에서 99.99% 로 가정되지만, 한국 통신 환경의 실측 (확인 필요) 으로는 (a) **FCM 도달률은 정상 환경에서 95~97%** — 안드로이드 제조사 (삼성·LG·중국 제조사) 의 doze / background restriction / FCM 자체 지연으로 단발 도달률 99% 미달. (b) **APNs 도 95~98%** — 백그라운드 / Focus 모드 / DND. (c) **NCP SENS 의 SMS 발송 성공률은 보통 98~99%** — 단 KT/SKT/LGU+ 의 스팸 필터 / 사용자 차단 / 번호 변경에 영향. (d) **자동 전화 (NCP Cloud Outbound Voice 또는 음성 SMS)** — TTS 변환 / 통화 연결률은 평균 80~90%, 부재중 / 통화 중 / 거절은 매우 흔함. 직렬 fallback (앱 실패 → SMS → 전화) 의 누적 도달률 ≈ 1 - (0.05 × 0.02 × 0.15) ≈ 99.985% 로 수학적으론 99.99% 가능. 단 **각 단계 사이의 시간 (앱 푸시 ACK 대기 → SMS fallback 발화) 이 직렬로 누적** 되면 5분 안에 다 못 끝낸다. 푸시 ACK 대기 30초 + SMS 대기 60초 + 전화 시도 60초 = 2.5분 + 발화 큐 대기 = 5분 직전. 큐가 막히면 SLA 깨짐. | (a) 다중화는 **병렬 발화** 로 명시 (앱 / SMS / 전화 동시 발화 후 첫 ACK 수신 시 나머지 취소). 직렬 fallback 은 5분 SLA 에 불리. (b) 각 채널의 ACK 정의 (전송 ACK / 수신 ACK) 를 명시. NCP SENS 의 SMS delivery report 는 LMS / MMS 와 일반 SMS 가 SLA / 가격이 다름 — 단가 비교 표 추가 권장. (c) 통화 자동화는 야간 / 휴일에 사회복지사 사적 시간 침범 — 윤리 / 노무 이슈도 한 절. (d) 5분 SLA 의 "각 채널 타임아웃 예산" 을 본문에 표로. |
| case §11.1 / 02장 §3.1 — "한전 AMI 연계 옵션 A (REST API) + C (sftp dump) 혼합" | 한전 AMI 의 실제 연계 방식은 (2026 상반기 시점, 확인 필요) 한전 측에서 **수요반응 사업자 (Aggregator) 만 직접 API 제공** 하고, 그 외는 대부분 **전력거래소 (KPX) 의 DR-MS / 분산자원 통합 운영시스템** 경유. 즉 동네에너지가 "한전 AMI 직접 API" 호출은 (1) Aggregator 라이선스 보유 또는 (2) 한전 위탁 사업자로 등록 — 두 조건 중 하나 필요. 책의 case §10.1 에 "한전 AMI 일 호출 한도 X (협의 가정)" 로 흐릿하게만 표시. 또한 (a) **AMI 데이터의 실시간성** — 한전 AMI 는 15분 단위가 표준이지만 가구별 데이터 전달은 보통 D+1 ~ D+3 지연. "실시간 DR" 은 한전 AMI 만으로 못 함 — **별도 게이트웨이 + 자체 측정 인프라 (CT/PT, 또는 가구 IoT 게이트웨이)** 가 필요. (b) **개인정보** — 가구 단위 AMI 데이터는 개인정보보호법 + 전기사업법의 개인정보 항목. 한전 → 동네에너지로 위탁 시 가구 동의 + 한전 위탁 계약 + 처리위탁 신고 (개인정보 처리방침) 모두 필요. | (a) case §7 외부 의존성 또는 §11.1 에 **"한전 AMI 연계 전제 (Aggregator 라이선스 / 위탁 사업자 등록)" 를 명시**. (b) "실시간 DR = 자체 IoT 게이트웨이 측정 + 사후 한전 AMI reconciliation" 의 2계층 구조를 본문에. (c) 02장 §3.1 의 "옵션 A + C 혼합" 은 **사실상 자체 IoT + 한전 AMI 의 2 데이터 소스 운영** 임을 명시 — 데이터 정합성 / reconciliation 의 추가 비용을 §3.4 또는 §7 (FinOps) 에. |
| case §11.1 / 02장 §3.2 — "세종시 데이터허브 양방향" | "양방향" 의 실제 운영 비용이 본문에서 빠짐. 세종시 데이터허브 (스마트시티 통합플랫폼) 는 (2026 시점, 확인 필요) FIWARE / NGSI-LD 표준 기반이거나 자체 표준일 수 있음 — 우리가 데이터 송신 시 (a) **NGSI-LD entity 변환 비용** (도메인 모델 ↔ 표준 모델 매핑), (b) **개인정보 비식별화 / 집계 처리** (가구 단위 → 동 단위), (c) **API 인증 토큰 / IP 화이트리스트 갱신**, (d) **시 데이터허브 측 점검 시간 (보통 새벽)** 에 동기화 깨짐 → 회복 로직. 수신 측 (시 → 우리) 도 (a) 데이터 신선도 (전기차 충전 위치가 5분 전 / 1시간 전 인지), (b) 시 데이터허브의 SLA (시민 서비스가 시 데이터허브 가용성에 종속됨 — 시 시스템 다운 = 우리 서비스 일부 다운). 25명 조직이 양방향 연동 운영 + 비식별화 + 변환 + 정합성 확인을 인프라 3명 + 백엔드 6명으로 한다 — **현실적으로 양방향 연계 운영에만 0.5~1명 FTE**. | (a) 양방향의 비용 (FTE / 인프라 / 점검 윈도) 을 §3.2 에 명시. (b) "시 데이터허브 의존도가 시민 서비스 가용성에 미치는 영향" 절 추가 — 시 시스템 점검 시 우리 서비스 자세 (degraded / fail-fast). (c) FIWARE / NGSI-LD 표준 채택 여부 + 표준 변환 라이브러리 (예: NEC FIWARE Orion) 사용 여부 명시. |
| case §11.1 / 02장 §11 — "ArgoCD self-host on NKS, 단일 인스턴스" | 단일 인스턴스 ArgoCD = SPOF. (a) ArgoCD 자체가 다운되면 GitOps 동기화 정지 — 긴급 핫픽스 시 kubectl 직접 적용 → 상태 drift, (b) Application controller / repo-server 의 단일 인스턴스는 5,000+ Application 운영 시 한계 (소규모는 OK), (c) ArgoCD self-host 는 ArgoCD 자체 업그레이드 부담 (분기 1회 minor 업그레이드). 25명 조직에서 ArgoCD self-host 운영은 실효 0.2~0.3 FTE — 매니지드 ArgoCD (Akuity / Codefresh) 또는 Flux 의 단순화 도 동등 옵션. | (a) ArgoCD self-host 의 SPOF / 업그레이드 / 백업 부담을 02장 §2.2 함정 박스에 추가. (b) Flux v2 (CRD 만으로 동작, UI 자체 호스팅 X) 의 단순성을 동등 옵션으로 비교. (c) ArgoCD ApplicationSet / Cluster 등록의 운영 패턴 1줄. |
| case §11.5 / 07장 §1.1 — "Grafana Cloud 처음부터" | Grafana Cloud 사용은 합리적. 단 (a) **데이터 주권** — 시민 IoT 메트릭 / 로그가 Grafana Cloud (현재 한국 리전 없음, 일본 / 싱가포르 / EU / US 중 선택) 로 나간다. 공공 위탁 계약상 "시민 데이터 한국 리전" 정책에 충돌. case §8 "데이터 주권 — 모든 시민 데이터는 NCP 한국 리전" 과 직접 모순. (b) **개인정보 식별 가능 메트릭** — 가구 ID / 디바이스 ID / IP 가 메트릭 label / 로그에 들어가면 그 자체가 개인정보. Grafana Cloud 로 나가는 데이터의 PII scrubbing pipeline 필요. (c) **비용** — 일 2,700만 record + 12 워크로드의 메트릭 / 로그 / 트레이스 Grafana Cloud 청구는 매월 수천 USD 가능. 매출 18~25% 인프라 비용에서 관측성 비중 추정이 본문에 없음. | (a) **공공 위탁 계약 + Grafana Cloud 의 데이터 소재지** 의 충돌을 02장 §5 에 한 절. 해결책 (NCP self-host Grafana / Loki / Mimir / Tempo + Object Storage backend) 를 동등 옵션으로 비교. (b) "메트릭 / 로그 / 트레이스에서의 PII 제거 파이프라인" 한 줄. (c) Grafana Cloud 비용 추정 (월 USD) — 1권 베타와 동일 요구. |
| case §6 / 02장 §5.1 — "IoT ingest 손실률 < 0.1%" | 0.1% 의 정의 (a) ingester 수신 후 DB 저장까지의 손실, (b) 가구 게이트웨이 → 클라우드 ingest 까지의 손실, (c) end-to-end (스마트미터 → 분석 가능) 의 손실 — 셋이 다 다른 수치. 한국 가정 LTE / 5G / 광랜의 평균 가용성은 99.5~99.9% (KT/SKT/LGU+) — **통신망만으로도 0.1~0.5% 가구 데이터 손실** 발생. 가구 게이트웨이 power outage / 사용자 코드뽑기 / 펌웨어 버그까지 합치면 end-to-end 손실률 1~3% 가 평균. **end-to-end 0.1%** 는 사실상 불가능 — 책의 SLA 가 ingester 내부 손실인지 명시 필요. | (a) "0.1% 의 측정 경계" 를 본문에 명시 (제안: CDSS 수신 이후 → DB 저장까지). (b) 가구 게이트웨이 → CDSS 의 손실은 별도 SLO (예: 가구 가용성 95% / 24시간 누적 손실률 5% 이하). (c) 손실 데이터의 **사후 보정** (DR 보상 시 한전 AMI 와 reconciliation 으로 누락 가구 보정) 로직을 §3.1 또는 §8 에. |

## 5. 잘 된 점 (3개 이내)

1. **"25명 / 220명" 의 결정 차이를 정면으로 다룬 관점** — 02장 §2.2 / 01장 §1.2 / 07장 §1.1 의 표는 한국에서 매우 드문 자료다. 1권 같은 "큰 조직 책" 만 있고, 작은 조직의 결정을 솔직히 다룬 책이 거의 없음. **이 책의 진짜 가치는 이 비교 자체** — 이 골격을 유지하면서 위 P1 / P2 항목의 사실 보강만 하면 한국 시장에서 독보적인 책이 된다.
2. **공공 협력 / 데이터 주권 / 시민 신뢰 KPI 의 명시적 다룸** — 01장 §4 / 02장 §3 / 07장 §4 의 "공공 위탁 영향 / 시민 신뢰 점수 / 공공 sponsor 비중 균형" 은 공공 SI 출신이 보기에 매우 정확한 진단. 특히 "sponsor 비중 30~70% 모두 위험 — 균형" 표 (07장 §4) 는 실무에서 자주 망각하는 진실.
3. **IoT 시계열의 골격을 PostgreSQL + TimescaleDB extension 으로 통일** — 02장 §2 / case §11.2.2. 25명 조직에서 DB 종류 늘리지 않으려는 의식적 결정으로 좋다. 단 위 P1 항목처럼 NCP TimescaleDB 매니지드 부재 / ClickHouse 동시 운영의 부담을 솔직히 추가하면 더 강해진다.

## 6. 종합 한 단락

> 출간될 만한가 / 누구에게 권할 것인가 / 출간 전 반드시 손볼 한 가지

이 책은 **출간될 만하다**. 1권의 "큰 조직 / AWS 중심" 을 보완하는 **작은 조직 / 공공 / 시계열** 의 정체성이 명확하고, 한국에서 이 영역을 정면으로 다룬 책은 거의 없다. 다만 인프라 영역에서 솔직히 짚으면 — **(1) "NCP 단일" + "인프라 3명" + "5분 안전 SLA 99.99%" 의 3 가지가 동시에 성립하지 않는다**. NCP 단일은 NCP 전체 장애 시 fallback 이 없고, 안전 알람 채널을 모두 NCP SENS 로 묶으면 SENS 장애 시 99.99% 가 깨지며, 인프라 3명으로는 NKS + 관측성 + 공공 협상 + 보안 + IoT 운영의 5개 역할을 1.67 FTE 부족하게 굴려야 한다. **(2) "한전 AMI 자동 식별" + "복지부 행복e음 자동 식별" + "세종시 데이터허브 양방향" 은 절차적 / 법적 / 운영적 무게가 본문 톤보다 훨씬 무겁다** — 한전 AMI 는 Aggregator 라이선스 / 위탁 사업자 등록이 전제이고, 행복e음은 민간 사업자 직접 연계가 거의 불가능하며, 세종시 데이터허브 양방향은 0.5~1 FTE 의 풀타임 연계 운영 부담을 동반한다. **(3) "Grafana Cloud" 와 "시민 데이터 한국 리전" 의 직접 충돌이 책 안에 미해결로 남아있다** — 데이터 주권 정책과 Grafana Cloud (현재 한국 리전 없음) 가 함께 등장하면 공공 위탁 계약 위반 가능성. **추천 독자**는 (a) 공공 / 스마트시티 / 에너지 / 헬스케어 / 안전 영역의 10~50명 조직 리드, (b) 1권을 읽은 후 작은 조직의 결정 차이를 보고 싶은 시니어, (c) 시계열 / IoT 입문자. 단 본 책의 케이스 (안전 SLA / NCP 단일 / 공공 연계) 를 그대로 자기 환경에 가져갈 때 위 3 가지 함정에 대한 자체 검증이 필수임을 본문에 명시할 필요가 있다. **출간 전 반드시 손봐야 할 한 가지**는 — case §6 "취약계층 안전 알람 99.99% / 5분" + case §8 "NCP 단일" + case §11.1 "외부 SaaS Grafana / Sentry" + 07장 §1 "인프라 3명" 의 **4 결정의 일관성 검증**. 권장 조합은 (a) 안전 알람 채널 중 최소 1개를 NCP 외부 (AWS SNS + Twilio Voice 등) 로 명시 + (b) "도달" 정의를 "전송 ACK" 와 "사회복지사 회신" 의 2단 SLO 로 분리 (전송 ACK 99.99% + 회신 95% / 15분) + (c) 인프라 3명의 시간 배분 표 + 외부 위탁 / 매니지드 보완 옵션 명시 + (d) Grafana Cloud 의 데이터 소재지 / PII scrubbing 정책을 case §8 의 데이터 주권 정책과 일치시킴. 이 한 가지가 정리되면 NCP / NKS / IoT / 공공 연계의 P1 / P2 항목은 다음 판본에서 점진 보완으로 충분하다.

---

> 이상. 솔직한 의견이 도움이 되길 바란다. 2권의 정체성 (작은 조직 / 공공 / 시계열) 자체는 한국 시장에 매우 필요한 책이다 — 위 일관성 한 가지만 정리되면 1권보다 더 좁고 더 깊은 책이 된다.
