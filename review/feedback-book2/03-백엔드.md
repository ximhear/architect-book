## 2. P2 — 다음 판본 보완 (운영 부채 / 사고 가능성)

| # | 위치 | 발견 | 제안 |
|---|------|------|------|
| P2-1 | 05-데이터 §3 continuous aggregate | `add_continuous_aggregate_policy` 예시는 좋은데, **실제 운영 함정** 이 누락. (a) `start_offset` 7 days 면 7일 지난 raw 만 집계되어 최근 데이터는 raw 만 조회 — 시민 앱 첫 화면이 raw 1,440 row 를 평균 내야 함, (b) `materialized_only = false` 면 raw + materialized 자동 합쳐 보임 (좋음) — 본문에 누락, (c) **continuous aggregate 자체에 인덱스 따로** 필요 — 본문 §9.2 "인덱스 누락" 한 줄로 합쳐져 있는데 분리. (d) hierarchical aggregate (1분 → 1시간 → 1일) 시 의존성 — 1분 집계 정책이 멈추면 1시간도 멈춤. | §3 에 "continuous aggregate 운영 4가지" 단락. + `refresh_continuous_aggregate` 수동 호출 (장애 후 catch-up) 방법. |
| P2-2 | 03-백엔드 §2.3 / 05-데이터 §3 | **시계열 압축 (TimescaleDB compression) 이 본문 어디에도 없음.** 5년 보존 (개보법 시행령) + 일 2,700만 record = 5년 누적 500억+ row. 압축 없이는 디스크 비용이 매출 18~25% IT 예산을 혼자 갉아먹음. compression policy 가 chunk 단위로 동작 + 압축 chunk 는 UPDATE/DELETE 불가 + reorder policy 와 충돌 — 시계열 운영의 절반은 압축 운영. | 05-데이터 §3 다운샘플링 절에 "압축 정책" 1/3 페이지. `ALTER TABLE ... SET (timescaledb.compress, timescaledb.compress_segmentby = 'household_id', timescaledb.compress_orderby = 'time DESC')`. 압축률 (보통 90% 이상) + 압축 후 쿼리 성능 / 압축 chunk 의 변경 불가 / decompression 비용. |
| P2-3 | 03-백엔드 §6 메시징 | **NCP CDSS Kafka 호환의 "호환" 깊이가 안 적혀있다.** CDSS 가 Kafka 프로토콜 호환이라 해도 (a) Schema Registry 가 자체 vs Confluent / Karapace 호환인지, (b) Kafka Streams / Flink 가 그대로 붙는지, (c) exactly-once semantics (idempotent producer + transactional producer) 가 동일하게 동작하는지, (d) MirrorMaker 2 / Connect 의 NCP 매니지드 여부 — 이 4개가 IoT ingest + DR 응답 설계의 전제. 본문 §6 한 표로 끝나면 시니어가 "이게 진짜 Kafka 처럼 동작하나?" 의심. | §6 에 "CDSS 의 Kafka 호환 — 어디까지 호환되는가" 한 단락. 모르는 부분은 "확인 필요 / 분기 단위 검증" 으로 명시 (CLAUDE.md 의 외부 사실 검증 톤). |
| P2-4 | 03-백엔드 §2.3 + 05-데이터 §3 | **"한전 dump 와 reconciliation 배치" 가 한 줄.** 손실률 0.1% 측정의 핵심인데 어떻게 비교하는지 안 적혀있다. 가구 단위 / 일 단위 사용량 비교 = 8,000 row × 5만 가구 = 일 4억 row 비교. PostgreSQL `EXCEPT` 로 단순 비교는 분 단위로 못 끝남. (a) 한전 dump 의 schema (CSV / fixed-width / XML), (b) timezone (한전은 KST 인지 UTC 인지), (c) DST / 누락 row 처리 (한전이 보고 안 한 가구), (d) 우리쪽 raw vs continuous aggregate 중 무엇과 비교 — 이런 운영 디테일이 손실률 SLA 의 진짜 어려움. | §2.3 reconciliation 단락 확장. 또는 05-데이터 §7 (공공 데이터허브) 옆에 "한전 reconciliation 흐름" 1/2 페이지. |
| P2-5 | 03-백엔드 §3.2 / 케이스 §11.2.4 | **DR 응답의 idempotency 키 설계가 한 줄.** "같은 시민이 두 번 누르면 한 번만" — 키가 `(household_id, dr_call_id)` 인가, `(household_id, dr_call_id, response_choice)` 인가? 후자면 시민이 "참여 → 거절" 로 마음 바꿔 누른 게 두 응답으로 기록. 전자면 마음 바꾼 게 무시. **DR 보상이 걸린 결정이라 둘 다 운영 사고 가능.** | (a) 키 정의 명시: `(household_id, dr_call_id)` + **last-write-wins with timestamp**, (b) 응답 변경 윈도우 (DR 호출 시작 후 5분까지만 변경 가능) 명시, (c) 변경 audit log — 추후 분쟁 시 "내가 거절했는데 참여로 기록됐다" 응대용. |
| P2-6 | 03-백엔드 §4.2 / 케이스 §11.2.4 | **세종페이 (지역화폐) 정산 흐름이 "일반 PG 와 다름" 한 줄.** 지자체 직불이면 환급 trigger 가 우리쪽 결정 (DR 보상 계산 완료) → 세종시 회계 시스템 (대개 분기 / 월 단위 정산) → 시민 지갑 입금. **사이에 며칠~몇 주의 지연**. 시민이 "DR 참여했는데 보상 안 들어왔다" 문의가 일 수십 건. 정산 상태 (계산 완료 / 세종시 회계 처리 중 / 입금 완료) 가 시민에게 노출되어야 함. | (a) 정산 상태 머신 명시 (3~4 상태), (b) 세종페이 정산 API 의 호출 빈도 / 응답 시간 / 실패 처리 — 외부 SaaS 가 아닌 지자체 API 라 SLA 가 약함, (c) 시민 알림 (각 상태 전환 시 푸시). |
| P2-7 | 03-백엔드 전체 | **백엔드 장에 "관측성" 절이 1권 베타 P1 과 똑같이 0개.** 게다가 2권은 25명 + 3명이 SRE 겸함 — 관측성 표준이 없으면 IC 풀 5명이 IoT lag / DR 응답기 backpressure / continuous aggregate 지연 / 모놀리스 GC pause 를 어떻게 한 화면에서 보는가. 그래파나 클라우드는 도구일 뿐 무엇을 대시보드로 만들지는 안 적혀있다. | 03-백엔드 끝에 "백엔드 관측성 최소 구성" 신설. (1) IoT ingester lag (Kafka consumer lag + TimescaleDB INSERT 지연), (2) DR 응답기 처리량 + 응답 분포 (응답까지 걸린 시간 p50/p95/p99), (3) continuous aggregate 갱신 지연, (4) 모놀리스 — 정산 큐 적체 / 세금계산서 발행 실패 / 분쟁 큐 적체. **취약계층 알람 5분 SLA 는 별도 SLO 대시보드 — 알람 발송 → 사회복지사 인지까지 trace.** |
| P2-8 | 05-데이터 §4, §5 / 03-백엔드 §3.3 | **DR 예측 + 취약계층 식별 모델의 "데이터 누수" 가능성이 빠짐.** 학습 데이터에 "다음 DR 응답" 이 들어가 있으면 데이터 누수. 가구별 시계열 split 시 시간 기준 split 안 하면 미래 정보 학습. XGBoost SHAP 설명 가능성이 좋다고 적혀있지만 SHAP value 가 시민에게 그대로 노출되면 ("당신은 30% 위험" 같은) 또 다른 사고. | (a) 모델 학습 시 시간 기준 split / 누수 검증 절차, (b) SHAP value 의 운영 노출 정책 (사회복지사에게는 노출 OK, 시민에게는 비공개), (c) 모델 drift 모니터링 (월간 정확도 drop 알람). |

## 4. 잘 된 점 (3개 이내)

1. **1권 베타가 짚은 "운영 관측성과 보상의 보상" 부재가 2권에서도 일관** — 같은 저자 / 같은 톤이라 일관성은 강점. 1권 베타에서 추가된 §관측성 / Saga 보상 실패 패턴을 2권 3장에도 이식하면 두 권 모두 운영 부채를 끊는 책으로 격상. (즉 같은 P1 을 두 번 짚게 됨 — 비난이 아니라 일관성 신호.)
2. **트레이드오프 표 형식 / 케이스 단일 출처 / "1권과의 비교" 표** — 8장 §3 의 19개 결정 비교 표는 1권 베타에서도 칭찬한 강점이 2권에서 한층 발전. 시니어 독자가 "내 환경은 1권에 가까운가 2권에 가까운가" 매핑이 즉시 가능.
3. **"시니어 친화" 의 일관된 제약 반영** — Access 30분 / PASS 우선 / MFA 면제 / 큰 글자 — 본 P1-5 에서 보안 트레이드오프 보완을 요구했지만, 시니어 / 취약계층을 NFR 으로 끌어올린 점 자체는 한국 백엔드 책에서 드문 강점. 1권 (전국 B2C) 의 "결제 99.99%" 와 다른 우선순위가 일관됨.

## 5. 종합 한 단락

이 책은 **출간할 만하다**. 1권의 사고 골격이 25명 조직 / 공공 협력 / 시계열 IoT 무대로 옮겨졌을 때 결정이 어떻게 갈라지는가의 시연이 일관되고, "케이스 단일 출처" 와 "1권과의 비교 표" 가 시니어 독자에게 즉시 가져갈 수 있는 도구를 준다. 다만 **백엔드 장 한정으로 출간 전 반드시 손봐야 할 것은 P1-1 (TimescaleDB hypertable 운영), P1-3 (DR 폭주의 auto-scale 시간), P1-4 (매칭 정산 / 세무 자동화의 외부 SaaS 강제), P1-5 (시니어 친화 인증의 보안 트레이드오프), P1-6 (대인 매칭 분쟁 1차 응대)** — 이 다섯이다. 1권 베타가 짚은 "운영 관측성 / Saga 보상 실패 / 인증 reuse detection" 이 2권에서 영역만 바뀌어 똑같이 빠져있다 (P2-7, P1-5). 시계열 영역의 운영 함정 (chunk_time_interval / compression / continuous aggregate / 인덱스) 은 PostgreSQL 운영 스킬과 별개라는 점이 본문 톤에 안 잡혀있어서, "PostgreSQL 통일로 운영 단순" 이라는 결정의 진짜 비용 — TimescaleDB extension 의 시계열 특화 함정 — 이 독자에게 안 전달된다. **DR 5,000 TPS 폭주 대응** 은 "Auto-scale 1 → 8 분당" 으로 너무 낙관적 — 실제로는 Kafka 가 폭주 버퍼이고 DR 응답기는 lag 안고 처리, 모놀리스 push 는 동기여서는 안 됨. 매칭 정산 / 세무 자동화는 25명 조직이 자체 구현하면 1년 안에 사고 — 외부 SaaS (이지샵 / 더존 / 케이크) 통합이 거의 강제라는 점을 솔직히 적어야 한다. 시니어 친화 인증의 보안 비용 (생활 패턴 추론 가능 데이터 + Refresh 60일 무검증) 은 1권의 결제 데이터 노출보다 윤리적으로 더 무거운데 트레이드오프가 한 줄. 대인 매칭 분쟁이 우리쪽 1차 응대라는 사실은 케이스의 가장 큰 운영 리스크인데 1차 응대 흐름이 본문에 없다. 이 다섯만 P1 으로 보완하면 2권은 **"같은 사고 골격이 다른 무대에서 어떻게 갈라지는가"** 의 시연이 완성된다 — 1권의 결제 운영 부채와 2권의 시계열 / 공공 운영 부채를 양쪽 다 끊어주는 한 쌍의 책으로 자리잡을 것이다.
