(b) 시니어 음성 정확도 한계 (WER 1.5~2배) 와 fallback (큰 버튼 + 전화 버튼) 을 본문에 명시. (c) HyperCLOVA X 도입 시점에 음성 입력도 Clova CSR (한국어 특화) 로 통일하는 결정 ADR. |
| 04-프론트엔드 4 (첫 화면 < 250KB + 한글 폰트 + 그래프) | "1권은 200KB. 2권은 250KB — 시니어 / 옥외용 큰 글자 / 그래프 라이브러리 부담 고려" — 무엇의 250KB 인지 정의가 빠짐 (1권 리뷰에서 이미 지적된 문제 그대로 답습). **Pretendard subset (KS X 1001) 만 80~120KB (gzip)**, Recharts 는 **min+gzip 약 60~80KB + D3 의존성** 이라 그래프 화면은 시작부터 200KB 가까이 채움. 더구나 그래프 라이브러리는 시민 앱 핵심 (전력 사용량 시각화) — 빠지면 안 됨. 그리고 시니어 큰 글자 모드 시 **Pretendard Bold / SemiBold 추가 필요** (얇은 글자는 노안에 안 보임) → subset 2배. 결론: **시민 웹 첫 화면 250KB 는 그래프 화면 한정으로 사실상 불가능**. | (a) "첫 화면 < 250KB" 정의 명시 — JS gzip vs 페이로드 전체. (b) 그래프 화면은 별도 예산 (예: < 400KB) — 또는 그래프를 정적 SVG (서버에서 미리 렌더) 로 갈아 클라이언트 그래프 라이브러리 제거. (c) Pretendard 는 unicode-range 동적 subset 으로 자주 쓰는 1차 자모 30~50KB + 나머지 lazy. (d) Recharts 대신 가벼운 옵션 (예: 직접 SVG path, 또는 Chart.js 의 tree-shaken 빌드) 비교 표. |
| 04-프론트엔드 3.1 (옥외 디스플레이 옥외 환경) | "옥외용 — 강한 햇빛 가독성 고려 (높은 대비 / 큰 글자)" — 햇빛 / 비 / 추위 / 영하 운영 / IP 등급 / 결로 / 화면 보호 / 야간 자동 밝기 / 화면 잔상 (burn-in) — **옥외 디스플레이의 실제 운영 변수가 한 줄로 뭉뚱그려져 있음**. 옥외 운영 경험상: (a) **세종시 겨울 영하 15도 + 여름 35도 + 습도 90%** 에서 일반 LCD 패널은 6개월 내 결로/패널 손상. **IP65 이상 + 산업용 패널 (HighBright 2,500 nit 이상)** 필수. (b) 햇빛 직사 시 **반사 방지 코팅 + auto brightness 센서** 없으면 일중 8시간 가독성 0. (c) Next.js Kiosk 모드는 SW 측면일 뿐, **단말 OS (Windows IoT vs Android Things vs Linux 임베디드) + MDM (모바일 단말 관리)** 가 더 큰 결정. (d) 단말 통신 끊어진 경우 (LTE 라우터 죽음) **오프라인 fallback 화면** 이 본문에 없음. 단순 "전체 화면 + 자동 새로고침" 으로는 옥외에서 1주일도 못 버팀. | 옥외 디스플레이 절을 **HW (패널·IP·온도) + OS·MDM + SW (Kiosk 모드 + 오프라인 fallback)** 3층으로 재구성. "Next.js Kiosk 모드" 는 SW 1층일 뿐. 운영 비용 / 단말 H/W 비용 / 통신 비용 (LTE 라우터 월 4~5만 원 × 동·면 수) / 유지보수 (분기별 청소·점검) 한 줄씩 추가. |
| 04-프론트엔드 2.2 (사업 시점 "확인 필요") | 4장 2.2 의 "확인 필요" 표시는 케이스 9 ("본 케이스가 가정하는 시점: 2026년 상반기") 와 결합하면 **2023년 「장애인차별금지법」 시행령 개정 (키오스크 접근성)** 이 이미 시행 중이라는 점에서 "확인 필요" 가 아니라 "시행 중" 으로 단호하게 적어야 함. 케이스 9 와 4장 사이 시점 불일치. | "확인 필요" 빼고 시점 (2026년 상반기) 기준 시행 중 조문 명시 — 「장애인차별금지법」 제21조 + 시행령 제14조 (2023년 개정 키오스크 항목 포함). |

## 2. 트레이드오프 / 균형 (B) — Priority 1 / 2

| 위치 | 발견 | 제안 |
|------|------|------|
| 04-프론트엔드 2.1 (단순 모드 default ON) + 7.2 표 | "단순 모드 (시니어 default)" 라고 적혀 있는데 **누가 시니어인지 판별 기준이 본문에 없음**. (a) 회원가입 시 생년월일로 자동 (65세 이상 default ON)? (b) 사용자가 직접 토글? (c) 운영자가 강제? — 이 결정이 빠져 있음. 65세 자동 ON 으로 가면 **연령 차별 (반대로 "노인 취급" 거부감)** 위험, 본인 토글로 가면 **단순 모드를 못 찾는 사람이 가장 필요한 사람** 이라는 역설. 그리고 단순 모드 ↔ 일반 모드 **전환 UI 자체가 시니어에게 안 보이는 곳에 숨겨지면 무의미**. 더 큰 문제 — 진단사 / 사회복지사가 시민 앱을 "대리 조작" 할 때 단순 모드 / 일반 모드 어느 쪽을 보는가? (취약계층 가정에 방문해서 같이 보는 경우 매우 흔함) | (a) default ON 결정 기준을 명시 — 권장: 회원가입 시 "큰 글씨로 보기" 옵션을 **첫 화면에 큰 버튼으로 묻기** (연령 자동 ON 은 차별 위험). (b) 전환 UI 를 홈 우상단 고정 큰 버튼 (작은 톱니바퀴 X). (c) "대리 조작 모드" — 사회복지사가 시민 앱을 같이 보는 시나리오 (방문 케어) 의 UX 결정. |
| 04-프론트엔드 5 + 7.1 (진단사·사회복지사 콘솔 디자인 시스템 공유) | "같은 모노레포에서 디자인 시스템 공유" — **공유 비중이 빠짐**. 시민 앱은 **단순 / 큰 글자 / 음성 / 그래프 최소** 인 반면, 진단사·사회복지사 콘솔은 **데이터 밀도 높음 (가구 100건 동시 모니터링) / 단축키 / 표 위주 / MFA 화면 / 다중 알람 처리** — 두 채널의 토큰은 공유 가능하나 **컴포넌트는 거의 별개**. 그런데 본문은 "공유" 한 단어로 뭉뚱그려 시니어 독자에게 "디자인 시스템 = 모든 컴포넌트 재사용" 인상을 줌. 작은 조직 (프론트 3명) 에서 디자인 시스템을 양쪽 모두 충족시키려 하면 **양쪽 모두 어중간** 해진다. | "공유: 토큰 (색·간격·타이포) + 기초 컴포넌트 (Button, Input) / 비공유: 도메인 컴포넌트 (시민 = 단순 카드 / 콘솔 = 대시보드 표·필터)" — 두 분리를 표로. 모노레포 `packages/ui` 는 토큰·기초만, 도메인 컴포넌트는 각 `apps/*` 내. 프론트 3명이 양쪽 모두 깊이 만들 시간이 없다는 트레이드오프 한 줄. |
| 04-프론트엔드 2.1 + 케이스 6 (DR 호출 5분 응답 SLA) | 케이스 6 운영 SLA: "취약계층 안전 알람 5분 이내 사회복지사 전달". 그리고 케이스 2.1 DR 호출: "순간 5,000 TPS / 1시간 내 1만 가구가 응답". 1만 가구 시민이 1시간 내 응답 = **평균 1인당 6초 안에 푸시 받고 확인 + 의사결정 + 응답** — 일반 성인도 빡빡, **시니어가 5분 이내 안정적으로 응답할 수 있는지** 의 UX 검증이 없음. 시니어는 (a) 푸시 알림 화면을 못 찾고 (홈 화면 알림 누적), (b) 푸시 누르고 앱 들어와도 어디서 응답하는지 못 찾고 (메뉴 깊이), (c) "참여" 버튼이 약속/실수 구분 안 됨 → **응답률이 일반 시민 대비 30~50%** 가 흔함. 그런데 본문에는 "DR 호출 알림 — 큰 글자 + 음성 알림" 한 줄로 끝. 5분 SLA 가 가능한가? | (a) DR 호출 시 시니어 단순 모드 화면을 **별도 sequence diagram** 으로 — 푸시 → tap → 큰 글자 "오늘 저녁 6~8시 절약하면 X 원" → 큰 버튼 2개 (참여 / 못함) → 1회 확인. (b) 푸시 미응답 시 SMS (NCP SENS) → 알림톡 → 전화 자동 — **4단계 fallback** 의 시니어 응답률 측정 KPI 한 줄. (c) "응답 못함" 도 안전 (취약계층 식별) 신호로 활용한다는 결정. |
| 04-프론트엔드 3.3 (옥외 디스플레이 보안) | "단말 별 토큰 (디스플레이 ID 인증) + 일정 시간 갱신" — **공공 광장 옥외 단말의 보안 위협 모델이 빠짐**. (a) USB 포트 노출 → 키보드 꽂으면 OS 직접 접근. (b) 전원 직접 차단 후 부팅 시 BIOS 진입. (c) 화면 캡쳐 / QR 코드 위조 (시민에게 가짜 URL 노출). ## 5. 잘 된 점 (3개 이내)

1. **단순 모드 / 일반 모드 분리 시도 자체가 한국 공공 책에서 드문 정직함.** 보통 "WCAG 준수" 한 줄로 넘어가는데, 4장 7.2 의 화면별 표 (홈 / DR 호출 알림 / 매칭 요청) 가 두 모드를 행으로 비교한 것은 의사결정 양식으로서 가치 있음. 시니어 독자가 자기 환경 (지자체 시민앱 / 복지앱) 에 그대로 가져가 양식을 채울 수 있다. (다만 default ON 결정 기준은 P1 에서 지적한 대로 보강 필요)
2. **옥외 디스플레이를 채널 일급으로 다룬 것 — 모바일 + 웹 + 어드민 3채널 책이 대부분인 시장에서 차별점.** 1권에는 없는 채널을 2권에서 새로 다룬 것은 "케이스가 바뀌면 채널도 바뀐다" 의 시연. 다만 옥외 운영의 깊이 (HW / 보안 / 운영 함정) 는 P1·P2 에서 지적한 대로 보강이 필요.
3. **공공 친화 컬러 (파랑·녹색) 결정에 "공공 신뢰 / 에너지 / 환경" 의 이유를 명시한 것.** 1권 (커머스) 의 컬러 결정 (브랜드 / 컨버전) 과 다른 결정 축임을 보여주는 좋은 사례. 단, 색맹·대비 검토는 P2 에서 보강 권장.

## 6. 종합 한 단락

이 책의 4장은 **시니어 / 취약계층 UX 를 정면으로 다룬 한국어 아키텍처 책 중 거의 첫 시도** 라는 점에서 출간 가치가 명확하다. 1권의 결제 컨버전 중심 프론트 결정과 2권의 접근성 중심 결정이 갈라지는 지점 — 단순 모드 / 음성 / 옥외 디스플레이 / 콘솔 분리 — 이 본문에 한꺼번에 모여 있어, 공공 / 복지 / 지자체 시민앱을 만드는 시니어 독자에게 매우 드문 자료가 될 것이다. 다만 4장은 **"공공 / 시니어 / 옥외에서 1주일 운영 후 실제 깨지는 부분"** 의 깊이가 부족하다 — (a) Web Speech API vs Native SFSpeechRecognizer / SpeechRecognizer 구분 누락 + 시니어 한국어 WER 1.5~2배 + 사투리·hesitation·동의어 함정 / (b) 옥외 디스플레이의 HW (IP65·HighBright·결로·온도) + OS·MDM + 오프라인 fallback 5층 누락 / (c) 첫 화면 250KB 가 그래프 + Pretendard + Recharts 결합 시 사실상 불가능한 점 / (d) 단순 모드 default ON 의 판별 기준 (연령 자동 vs 본인 선택) 결정 누락 / (e) DR 호출 5분 응답 SLA 가 시니어에게 현실적인가의 sequence + 4단계 fallback (푸시 → SMS → 알림톡 → 전화) 누락 / (f) 「장애인차별금지법」 시행령 (2023 키오스크 항목) 적용 누락 / (g) 진단사·시공사가 현장 (가정 방문) 에서 쓸 모바일 형태 (PWA?) 누락 / (h) 프론트 3명이 6개 채널 디자인 시스템을 운영하는 비용의 트레이드오프 누락 — 이 8가지 중 본문에 정면으로 다뤄진 것이 1개 (단순 모드 분리 시도) 뿐이라, 책 따라 만들면 "시범 운영 1개월은 잘 되는데 옥외 단말이 영하 10도 첫 추위에 죽고, DR 호출 시 시니어 응답률 30% 도 안 되고, 진단사가 현장에서 못 쓴다." 가장 권하고 싶은 독자는 **공공 / 지자체 / 복지 영역에서 시민앱을 처음 설계하는 시니어 백엔드 또는 풀스택 아키텍트** 이고, **출간 전 반드시 손봐야 할 한 가지는 "옥외 Kiosk 의 HW + OS + MDM + Kiosk 모드 + 오프라인 fallback 5층 + 옥외 운영 함정 5가지 박스 + KWCAG 키오스크 접근성 절"을 4장 3절에 추가하고, 8장 결정표에 6개 채널을 모두 한 줄씩 정리하는 것"** 이다 — 이 책이 "옥외 디스플레이를 채널 일급으로 다룬" 차별점을 살리려면 옥외 깊이가 모바일 깊이만큼 들어가야 한다.
