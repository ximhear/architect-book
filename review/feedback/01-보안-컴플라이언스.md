## 1. 사실 / 정확성 (A)

### P1 (반드시 고쳐야 함)

| 위치 (파일:절) | 발견 | 제안 |
|---|---|---|
| 06장 1.2 / 1.4 / case-study 5.1 | **ISMS-P 의무 대상 기준이 모두 "확인 필요" 로 회피됨**. 입문서라도 의무 대상의 핵심 수치는 명시해야 한다. 현행 「정보통신망법」 제47조 + 시행령에 따른 ISMS 의무 대상은 (1) 정보통신서비스 매출 100억 이상, (2) 일평균 이용자 100만 명 이상, (3) 기간통신/IDC 등이며 ISMS-P 는 **별개의 자율 인증** 이다. 책은 "ISMS-P 의무 대상" 이라 단정하는데 이는 부정확하다 — ISMS 가 의무이고 ISMS-P 는 개인정보 영역까지 포함한 확장 인증이지 의무 자체가 다른 별개 제도가 아니다. | "ISMS 의무 대상이며, 개인정보 처리량을 고려해 ISMS-P 를 자발적으로 취득" 으로 정정. 그리고 매출 100억·이용자 100만 명 기준을 본문에 명시 (시행령 조문 번호 + "최신 조문 직접 확인" 한 줄로 충분). |
| 06장 8.2 / 1.4 | **사고 통지 시한이 "확인 필요" 로 모두 회피**. 베타리더 입장에서 가장 위험한 누락. 「개인정보 보호법」 제34조 + 시행령 제40조에 따른 유출 통지/신고는 (a) 정보주체 통지: **지체없이 (5일 이내)**, (b) 개인정보보호위원회/KISA 신고: **1천 명 이상 유출 시 72시간 이내** 가 현행 기준이다 (2023년 시행령 개정). 책 출간 시점에 이 숫자가 비어있으면 "이 책은 보안을 다룬다고 말만 한다" 가 된다. | 본문에 "정보주체 통지 5일 이내, 보호위/KISA 신고 72시간 이내(1천 명 이상 유출 시)" 명시. 신고처도 "보호위·KISA" 로 정확히. KISA 단독 아님. |
| 06장 1.3 "결제 직접 처리 회피" | **"PG 위탁이라도 본인 책임" 목록이 너무 얕다**. 실제 전금법 위탁자 책임 (전자금융감독규정 제13조 등) 은 (1) 위탁업무 점검 의무 (연 1회 이상), (2) 위탁받은 자에 대한 관리감독, (3) 사고 발생 시 1차 책임은 위탁자, (4) PG 에 대한 보안취약점 점검 결과 수령 의무 등 훨씬 무겁다. 위탁했다고 책임이 사라지지 않는다는 점이 입문서에서 가장 중요하다. | "PG 위탁=책임 면제 아님" 을 강조하는 박스 1개 추가. 위탁 점검 의무 (연 1회 이상), 위탁계약서 필수 포함 사항 (개인정보 보호법 제26조), 사고 시 1차 책임 소재를 명시. |
| 06장 2.5 암호화 표 | **"비밀번호 — bcrypt / Argon2id, salt 16바이트+"** 표기가 부정확하다. (1) bcrypt 는 salt 를 알고리즘이 자체 생성하며 길이는 16바이트 고정이다 — 사용자가 "16바이트+" 로 늘릴 옵션이 없다. (2) Argon2id 의 salt 권장은 RFC 9106 기준 **16바이트 이상** 이지만 메모리/병렬도/시간 파라미터 권장값 (m=19MiB, t=2, p=1 minimum 또는 OWASP 권장 m=64MiB 등) 이 빠지면 의미가 없다. cost 만 말하고 메모리 인자를 빠뜨리는 게 가장 흔한 사고 원인. | bcrypt 는 cost 10~12 권장 (CPU 발전에 따라 12 권장이 2026년 현실). Argon2id 는 OWASP 2024 권장 파라미터 (m=19MiB, t=2, p=1 또는 m=64MiB, t=3, p=4) 를 한 줄 추가. salt 는 알고리즘이 처리한다는 점 명시. |
| 06장 3.1 / 1.4 | **본인인증 / 주민번호 처리 부분이 위험할 정도로 얕다**. 「주민등록번호 처리 제한」 (개인정보 보호법 제24조의2) 은 법령에 근거가 있는 경우 외에는 **수집·저장·이용 자체가 금지** 다. 본인인증 사업자 (NICE/KCB/PASS) 를 통한 CI/DI 만 받는 것이 표준이며 "해시 + CI" 라고 한 줄로 끝낼 영역이 아니다. CI 와 DI 의 구분 (CI: 사이트 간 동일인 식별 / DI: 사이트 내 중복가입 방지) 이 빠지면 셀러 멀티계정 차단 룰 (7.2의 1번) 자체가 작동 불가. | 2.1 표에 "주민번호" 행을 별도로 두고 "수집·저장 원칙적 금지, 본인인증 사업자 통한 CI/DI 수령 only" 명시. CI/DI 를 약어 풀이 + 용도 차이로 구분. 7.2 의 다중계정 룰도 "DI 기준" 으로 정정. |

| 06장 2.5 PCI-DSS | **"카드 정보를 자체 저장할 때만"** 으로 단정했으나, 실제로는 "카드번호를 처리·전송·저장하는 모든 조직" 이 대상이다. PG 위탁이라도 카드번호가 우리 서버를 한 번이라도 거치면 (예: 토큰화 전 평문이 webview 가 아닌 백엔드를 통과) PCI-DSS Scope 에 들어간다. | 06장 6.3 멀티테넌시 | **"`WHERE seller_id = ?` 강제 (애플리케이션 레이어)"** 는 실무 사고 회고에서 가장 자주 깨지는 곳. ORM 의 글로벌 필터 / Hibernate `@Filter` / JPA 인터셉터 / MyBatis Plugin 같은 **강제 메커니즘** 을 언급해야 한다. "강제하라" 만 하고 도구 이름이 없으면 코드리뷰로만 막다가 한 번 빠진다 (실제 사고 패턴). | "Spring Boot/Kotlin 기준 Hibernate `@Filter` + JPA 인터셉터 / MyBatis SqlInjector 로 강제" 한 줄 추가. RLS 와 결합한 2중 방어 구조 (앱 + DB) 도 다이어그램으로. |
| 06장 7.2 어뷰징 0단계 룰 | **"동일 디바이스 5계정 이상" 룰의 "디바이스" 식별이 무엇으로 되는가** 가 빠짐. FingerprintJS 같은 핑거프린트는 (a) 정확도 60~80%, (b) 사용자 동의 필요 (개인정보 보호법상 식별자 처리), (c) iOS Safari 의 ITP 로 무력화될 수 있음. 이 한계를 모르고 룰만 적용하면 false positive 로 정상 사용자 차단 사고가 난다 (실제 회고 사례 다수). | "디바이스 식별의 한계 — IDFA/AAID 동의, 핑거프린트 정확도, ITP" 박스 1개 추가. CI/DI (개인) + 디바이스 ID (기기) + 결제수단 ID (카드 BIN+last4) 의 3중 조합으로 정확도 올리는 게 실무 표준. |
| 06장 8.1 사고 대응 흐름 | **"보존" 단계 (Preservation / Forensic Imaging) 가 빠졌다**. 격리 → 영향범위 → 원인분석 사이에 "증거 보존" (메모리 덤프, 로그 스냅샷, 디스크 이미지) 이 들어가야 사후 법적 대응이 가능하다. 격리하고 바로 분석/복구 들어가면 evidence 가 휘발돼 사고원인 입증 불가 + 형사고소/보험청구 시 곤란. | flowchart 에 `Preserve[증거 보존<br/>덤프·스냅샷]` 노드를 Isolate → Scope 사이에 추가. |

### P2

| 위치 | 발견 | 제안 |
|---|---|---|
| 06장 4.2 결제 다중화 | **"PG 3사 자동 fallback"** 의 위험한 측면이 빠졌다. (a) 같은 카드를 3사에 연속 시도 → 카드사가 의심거래로 차단, (b) 1차 PG 의 응답 지연 (timeout) 후 2차 시도가 1차 결과와 충돌해 이중결제, (c) 정산 reconciliation 의 복잡도 폭증. fallback 은 만능이 아니다. | trade-off 표 — "Fallback 적극 / 보수적 / Manual 재시도" 3안. 이중결제 방지를 위한 idempotency_key 의 PG 간 공유 방안 (어차피 못 한다는 점) 명시. |

## 5. 잘 된 점 (3개 이내)

1. **6.3 멀티테넌시 격리** 가 RLS + 애플리케이션 + IDOR 방지를 한 묶음으로 다룬 점 — 입점 셀러 모델에서 가장 자주 빠지는 영역인데 입문서가 명시한 점이 좋다 (단 MySQL 호환성 정정 필요 — C 의 P1 참조).
2. **7.2 어뷰징 0단계 룰 3개로 시작** — 입문서가 ML/SaaS 부터 권하지 않고 "룰 3개 → 운영" 으로 작게 시작하는 사다리를 그린 점이 매우 현실적. 다만 "디바이스 식별의 한계" 와 "ML 진입 전 충분조건" 은 보강 필요 (A·B 의 P2 참조).
3. **6장 1.4 + 4 + 8 의 외부 의존성·법규·사고대응이 케이스 7 (외부 의존성), 케이스 5.1 (법규) 와 번호로 인용되어 단일 출처 원칙이 잘 작동** — 챕터-케이스의 일관성 측면에서 ADR-0008 의 가치가 보안 챕터에서 잘 살아남.

## 6. 종합 한 단락

이 책의 보안 챕터는 **"입문서로서의 폭" 은 합격, "실무 정확성" 은 출간 전 손볼 곳이 많다.** 가장 큰 문제는 핵심 법규 수치 (ISMS 의무 기준, 개인정보 유출 통지 시한, CISO 신고 기준) 가 모두 "확인 필요" 로 회피된 점이다 — 보안을 다루는 챕터에서 13회의 "확인 필요" 는 신뢰를 무너뜨린다. 또한 RLS 를 권하면서 케이스의 주 DB 가 RLS 미지원 MySQL 인 모순, PG 위탁자의 책임 한계 누락, ISMS-P 심사 단골 항목 (위탁자 관리, 접속기록 보존 1~2년, 암호키 관리, DR 모의훈련) 이 통째로 빠진 점은 실제 심사 한 번이라도 들어가본 사람의 눈에는 바로 보인다. **출간하기에 부족하지는 않지만, 1차 인쇄 전에 P1 5개 + 누락 항목 5개는 반드시 손봐야 한다.** 출간된다면 가장 권하고 싶은 독자는 **"보안팀이 따로 없는 시리즈 A~B 스타트업의 백엔드 시니어"** 다 — ISMS-P 의무 직전 단계에서 "무엇부터 봐야 하는지" 의 지도로 가치가 크다. 반대로 이미 ISMS-P 인증을 받은 회사의 보안 담당자에게는 깊이가 부족하다 (그건 별도의 책의 영역). **출간 전 반드시 손봐야 할 한 가지를 꼽는다면**: "확인 필요" 박스 13개를 모두 (a) 집필 시점 기준 단정 + (b) 챕터 첫머리 "법규 인용 주의" 박스 1회로 통합 — 이 정리만 해도 책의 신뢰도가 한 단계 올라간다. 그 다음 우선순위는 RLS·MySQL 호환성 정정과 "PG 위탁자의 책임" 박스 추가다.
