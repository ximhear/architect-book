## 1. 사실 / 정확성 (A)

## 2. 트레이드오프 / 균형 (B)

| 위치 | 발견 | 제안 |
|------|------|------|
| 04-프론트엔드 1.1 결정 (Native 2벌) | 결정은 맞다고 보지만, **"Android 14명 + iOS 12명 = 26명" 이 인력 2배 비용을 정당화하는 근거** 가 빠짐. 케이스 4 의 26명은 RN 으로 가면 17~18명으로 줄지 모르나, RN 인력 채용난(특히 시니어) + 신규 OS 대응 지연 비용 / 라이브 영상 모듈 직접 구현 비용을 합치면 결국 비슷하거나 더 비싸진다 — 이 계산이 본문에 한 줄도 없다. 독자가 "그럼 우리도 RN 해도 되겠네" 라고 잘못 가져가기 쉬움. | "원픽이 Native 를 택한 이유" 절에 인력 트레이드오프 + 라이브 / 결제 SDK 두 화면이 RN 에서 가장 비싸진다는 구체 사례 한 줄 |
| 04-프론트엔드 2.2 (상품 상세 ISR) | **800만 SKU (활성 300만) 를 ISR + on-demand revalidate 로 전부 깔면 CDN edge 캐시 키 폭발 + 빌드 매니페스트 거대화 + revalidate 큐 폭주** 가 거의 확정적이다. Vercel 기준으로 150만 path 넘어가면 ISR 빌드 자체가 어려워지고, 자체 호스팅이어도 .next/server/app 디렉토리가 GB 단위로 부풀어 EKS pod 띄우는 시간이 길어짐. **상위 50만 SKU 만 ISR + 나머지 SSR + Stale-While-Revalidate 헤더로 CDN 캐시** 가 현실적. 표에 비용 비교가 빠짐. | ISR 적용 범위를 "Top N SKU" 로 한정 + 나머지는 SSR/CDN 캐시 라는 두 단계 전략 추가. "ISR 비용 = path 수 × revalidate 빈도 × 빌드 비용" 한 줄 |
| 04-프론트엔드 4.3 (모바일 GraphQL BFF) | BFF GraphQL 의 **백엔드가 Spring Boot 모놀리스 (Kotlin)** 인데, gRPC 도 REST 도 아닌 GraphQL BFF (Node.js Apollo) 사이 통합이 어떻게 일어나는지 빠져 있다. 보통 (a) GraphQL BFF → 모놀리스 REST 호출 (b) GraphQL BFF → 모놀리스 gRPC 호출 두 가지인데, 케이스 11.2.2 에는 "내부 서비스 간 gRPC" 라고 적혀 있다. 즉 BFF 가 모놀리스에 gRPC 로 붙는다는 건데 — Spring Boot Kotlin gRPC + Node.js Apollo 조합은 **DataLoader + protobuf 코드 생성 + N+1 캐싱** 이 만만치 않다. 이 통합 비용이 한 줄도 없음. | "GraphQL BFF ↔ Spring 모놀리스 통합" 절 한 단락 — DataLoader / N+1 / 스키마 동기화 (CI 게이트) / 실패 격리 |
| 04-프론트엔드 5.3 (MFE 미도입) | 결정은 동의하나 **"단일 Next.js 앱 + 도메인팀 자율 배포" 가 사실상 양립 불가능** 하다는 점이 빠짐. apps/web 한 곳에 220명 중 도메인팀 N개가 PR 을 던지면 (a) 배포 충돌 주 5건이 그대로 클라이언트로 옮겨오고 (b) Next.js Turbopack 빌드 시간이 SKU 페이지 + 카테고리 page 가 늘어날수록 폭증. 모놀리스 백엔드의 빌드 12분 / 배포 25분 신호와 똑같은 일이 클라이언트에서 일어남. **route group 단위 코드 오너십 + Vercel Preview 의 도메인팀별 환경 + Module Federation 까지는 아니어도 dynamic import 단위 분할** 로 풀어야 함. | "도메인팀 자율 배포의 클라이언트 측 부담" 절 추가, 또는 4.3 "1년 후 재검토" 조건에 "웹 PR 충돌이 백엔드 모놀리스 수준이 되면 MFE 재검토" |
| 04-프론트엔드 9.2 (라이브 LL-HLS + WebSocket) | **WebRTC 가 표에서 "지연 vs 안정성" 한 줄로만 다뤄지고 결정에서 빠짐**. 동접 1만 라이브 + 호스트 ↔ 시청자 양방향 (예: "이 옷 입어보세요") 이 들어오는 순간 LL-HLS 만으론 2~5초 지연이 한계, WebRTC SFU 가 필요하다. 표에서 "원픽은 시청자 단방향이라 LL-HLS 로 충분" 명시가 없으면 독자는 양방향 라이브를 LL-HLS 로 깔다가 죽음. | 라이브 결정에 "양방향 인터랙션 (호스트-시청자 음성/영상) 이 있으면 LL-HLS 만으로 부족, SFU 검토" 한 줄 |
| 04-프론트엔드 4.3 (웹 BFF = Next.js Server Action) | Server Action 이 BFF 역할을 한다는 건 맞지만, **Next.js Server Action 은 RPC 본질 — POST 만 / FormData 우선 / 캐시 키 명시적 관리 안 됨** 의 제약이 있음. 검색·필터처럼 GET 로 캐시 가능한 영역에는 Route Handler 가 맞고, 폼/주문 같은 mutation 은 Server Action 이 맞다. "Server Action / Route Handler" 라고 묶어 둔 표현이 두 도구의 적용 영역을 흐림. | 표 또는 한 단락으로 "Server Action = mutation, Route Handler = GET / 캐시 / 외부 webhook 수신" 분리 |

## 4. 독자 입장 — 너무 추상 / 너무 세부 / 누락 / 사족 (D)

| 위치 | 어떻게 읽혔는가 | 제안 |
|------|---------------|------|
| 04-프론트엔드 3.3 webview | "origin 검증 필수" 만 적혀 있다. 시니어 독자는 "어떻게 검증?" 을 알고 싶다. **카카오페이/네이버페이/토스페이 SDK 의 webview 흐름이 각각 다르고**, native bridge 인터페이스가 (a) JavaScriptInterface (Android) / WKScriptMessageHandler (iOS) (b) custom URL scheme (`merchantapp://`) 두 갈래로 나뉘는데, intent scheme 처리 (Android) · `LSApplicationQueriesSchemes` (iOS Info.plist) 등 실제 함정이 본문에 한 줄도 없다. 한국 모바일 결제의 가장 큰 사고는 origin 검증보다도 **앱 미설치 시 fallback (스토어 이동) 처리 누락** 임. | "한국 결제 webview 의 4가지 패턴 — JS bridge / custom scheme / intent scheme / universal link" 표 추가. 또는 짧은 시퀀스 다이어그램 |
| 04-프론트엔드 8.2 외부 SDK | "광고 · 분석 SDK 가 LCP 의 가장 큰 적" 만 있고, 한국 특수 SDK 가 빠짐 — **카카오 채널톡, 채널톡, 네이버 애널리틱스, 카카오 픽셀, 네이버 광고 픽셀, Wisetracker, AppsFlyer** 가 거의 모든 한국 커머스에 다 들어간다. 이 7~10개 SDK 를 어떻게 facade 패턴으로 격리하는지 한 줄도 없음. | "한국 커머스의 외부 SDK 평균 7~10개 — facade 패턴 + Tag Manager (GTM) 로 lazy load" 한 단락 |

## 5. 잘 된 점 (3개 이내)

1. **케이스 11.3 의 채널별 기술 스택과 BFF 매핑이 깔끔하다.** 한국 시장에서 "모바일 GraphQL BFF + 웹 Next 자체 BFF + 어드민 REST 직접" 의 세 갈래는 실제 운영 회사들의 평균에 잘 맞고, 굳이 모든 채널에 BFF 를 강요하지 않는 균형이 좋다.
2. **렌더링 전략 표 (2.2) 가 화면별로 근거를 적어둔 게 큰 강점.** "메인 SSR + 캐시 5초", "장바구니 CSR" 처럼 이유와 함께 결정한 패턴은 시니어 백엔드 출신이 처음 프론트 결정 들어가도 따라가기 쉽다. 시퀀스 다이어그램 4.1 에서 "가격·재고는 클라이언트에서 갱신" 이 그림으로 들어가 있는 것도 좋음.
3. **Native 2벌 결정의 근거에 "결제 / 라이브 영상 / 푸시 안정성 / 국내 SDK 호환성" 4개를 명시한 것이 한국적이다.** RN/Flutter 의 일반론적 비교만 늘어놓는 책이 많은데, 원픽이 왜 Native 인지 한국 SDK 사정을 들어 설명한 건 책의 정체성 ("한국 시장 한정") 과 잘 맞는다.

## 6. 종합 한 단락

이 책은 "프론트엔드 시니어 → 아키텍트" 전환자에게 **출간될 가치가 충분히 있다**. 특히 BFF · 디자인 시스템 · 채널 전략 · ADR 형식의 큰 그림은 한국에 이런 입문서가 거의 없는 영역이라 시장 가치가 명확하다. 다만 4장은 현재 **"한국 모바일에서 명절 트래픽에 실제로 죽는 부분"** 의 깊이가 부족하다 — 800만 SKU ISR 의 비용 폭발 / 라이브 채팅 fanout 의 임계 / Spring 모놀리스와 Node.js Apollo BFF 통합의 실무 / 결제 webview 의 한국 4가지 패턴 (JS bridge · custom scheme · intent scheme · universal link) / 한국 외부 SDK 7~10개의 LCP 압박 / IME composition 함정 / 한글 폰트 subset 의 이름 누락 사고 — 이 7가지 중 본문에 정면으로 다뤄진 것이 거의 없어, 책 따라 만들면 "베타까지는 잘 되는데 명절날 라이브 + 결제 + 검색이 동시에 들어오는 순간 죽는다." 가장 권하고 싶은 독자는 **백엔드 시니어가 아키텍트로 전환하면서 프론트 결정을 같이 봐야 하는 사람** 이고 (프론트 시니어에게는 1.1~1.2, 4장 5절은 이미 알고 있는 내용이라 가성비가 떨어짐), **출간 전 반드시 손봐야 할 한 가지는 "원픽이 명절·라이브 동시 트래픽에서 깨질 수 있는 프론트 측 실패 시나리오 1개를 9장 또는 4장 끝에 시퀀스 다이어그램으로 추가하는 것"** 이다 — 이 책의 모든 결정이 "왜 이렇게 했는지" 는 잘 적혀 있는데 "이 결정이 깨지면 어떻게 죽는지" 가 빠져 있어, 시니어가 자기 환경에 가져갈 때 가장 중요한 위험 감각이 안 생긴다.
