## 1. 사실 / 정확성 (A)

| 위치 (파일:절 또는 줄) | 발견 | 제안 |
|---------------------|------|------|
| case-study §11.1 / 02장 §8 | "EKS — 서비스 약 80개" + Lambda + Linkerd + Tempo + Loki + Prometheus + Grafana Cloud + Atlantis + ArgoCD + ALB Ingress + External Secrets — 이걸 운영하는 SRE 가 **8명** ([케이스 §4](../../manuscript/case-study/README.md#4-팀-구조)). 현실 운영 인력 기준으로 **부족하다**. EKS 80 워크로드 + Linkerd 사이드카 + Tempo/Loki self-host + Atlantis = 최소 SRE 12~15명, 또는 관측성·서비스메시 일부를 Datadog/AWS 관리형으로 잘라야 한다. 현재 구성은 "8명이 풀가동해도 일상 운영 + 온콜 + 이슈 대응 + 비용 최적화 모두 못 한다" 가 거의 확실. | (a) SRE 8명을 유지하려면 Linkerd 빼거나(또는 ASM/AppMesh로 전환), Loki/Tempo 를 Grafana Cloud 통합본 또는 Datadog 으로 잘라라. (b) 또는 SRE 인원을 12~15명으로 케이스에 반영하라. (c) 본문에 "스택 폭 = SRE 인원" 환산표를 명시하라. |
| case-study §11.1 / 02장 §8 | **Linkerd 선택 근거**가 "단순성·낮은 오버헤드" 한 줄. 실제로 Linkerd 는 mTLS·tap·골든 메트릭은 좋지만 (1) **국내 한국어 자료/사례 거의 없음**, (2) 외부 컨설팅 풀 매우 작음, (3) Helm chart breaking change 가 있어 업그레이드 부담, (4) Istio 보다 운영 익숙한 인력 시장이 훨씬 작음. EKS 80 + 도메인팀 자율 환경에선 mTLS·관측성 효과 대비 **운영 부채**가 더 큼. | "왜 Istio 가 아닌가" 비교를 명시. 또는 "메시 미도입 + 앱 SDK 레벨 OTel + ALB mTLS" 옵션을 동등하게 제시. 한국 인력 시장 현실은 책의 강점인데 이 절에선 빠짐. |
| 02장 §1.1 — 클라우드 비교표 | "NCP 한국어 지원·결제 편의·한국 리전 다양 / 글로벌 대비 서비스 깊이 얕음" 까진 OK 인데 핵심 함정 누락: (a) **NCP 의 매니지드 Aurora/Kafka/OpenSearch 등가 서비스가 부족하거나 늦음** — Cloud DB for MySQL 은 Aurora 호환 아님, Cloud Data Streaming Service 는 MSK/Confluent 대비 운영 도구·성숙도 격차, (b) **NCP Kubernetes Service (NKS) 의 노드 그룹 / 오토스케일링 동작이 EKS 와 미묘하게 다름** — 동일 매니페스트 못 옮김, (c) **NCP Object Storage 와 S3 호환성 부분적**. "결제 백엔드 일부를 NCP" 라고 가볍게 쓰지만 실제론 Aurora→Cloud DB 전환 + Kafka→CDSS 전환 + IAM·태그 정책 재구축 모두 필요. | NCP·KT·NHN 의 "AWS 등가 서비스 격차" 표 한 장 추가. 특히 "결제 NCP 이중화 RTO 5분" 은 **DB 까지 동기 복제 가능한 구성을 NCP 가 제공하는가** 를 사실 확인하고, 안 되면 본문 SLA 표(99.99% / RPO 0 / RTO 5분) 를 수정해야 한다. |
| case-study §6 / 07장 §2.3 — 결제 SLO | **결제 99.99% + RPO 0 + RTO 5분 + p95 2s** 동시 충족은 매우 도전적. 99.99% = 월 4.32분 다운. RPO 0 = 동기 복제. RTO 5분 = AWS↔NCP 자동 페일오버 자동화·DNS 전환·세션 이전·PG 재라우팅 모두 5분 안. 현실에서 멀티 클라우드 액티브-액티브 결제는 (1) 연 비용 단일 대비 2~3배, (2) PG 와의 콜백 URL·화이트리스트 양쪽 등록, (3) 양쪽 idempotency key 충돌 처리, (4) 세션 동기화. **8명 SRE + 결제팀 12명 으로 1년 안에 RTO 5분은 무리**. 분기별 로드맵에서 Q2 에 "NCP 100% 이중화" 한 줄로 적힌 것은 위험. | (a) 결제 SLO 를 99.95% (월 21.6분) 로 현실화하거나, (b) RPO 0 을 RPO 30초~1분으로 완화하고 보상 트랜잭션 의존하도록 명시, (c) "RTO 5분" 의 실제 의미 (수동 페일오버 vs 자동) 를 본문에 명시. Q2 "결제 분리 + NCP 100% 이중화" 는 1분기로는 **불가능**. 12~18개월 사업으로 표시. |
| case-study §10.1 / 08장 §4.3 | "에러 버짓 분기 평균 70% 소진" — 99.99% 의 70% 는 분기 가용성 99.997% 정도에 해당. 결제 SLI 측정 정의 (PG 콜백 5xx? 사용자 결제 완료율? 응답시간 SLO 위반?) 가 본문에 없어 70% 라는 수치가 추상적. 또한 70% 면 "빠듯" 이 아니라 "정상" 이다 — 정상 운영의 에러 버짓은 보통 50~80% 소진된다. 90% 소진이 "위험 신호". 이 경계선이 본문에서 흐릿함. | (a) 결제 SLI 를 "결제 시도 → 최종 성공" 사용자 관점 비율로 정의 명시, (b) "70% 소진" 을 "분기 70%, 90% 소진까진 5%p 여유" 같은 식으로 표현. "빠듯하다" 는 표현을 데이터로 뒷받침. |
| 02장 §5.2 / 07장 §10.3 | "Loki + S3 archive" / "Tempo + Grafana" — 일 로그 2~5TB ([케이스 §2.2](../../manuscript/case-study/README.md#22-데이터)) 를 Loki self-host 로 받으면 **Loki 운영 자체가 풀타임 1~1.5명**. 인덱스 설계, ingester/querier 분리, S3 lifecycle, Boltdb-shipper / TSDB 마이그레이션, 카디널리티 폭발 방지. 트레이스 1% 샘플링이라도 EKS 80 워크로드면 일 수 GB. Tempo + Grafana Cloud 무료 티어로는 절대 안 됨. **Grafana Cloud 가 매월 수만 달러 청구되거나 self-host Loki 가 SRE 1.5명 빨아먹는다** — 둘 중 하나. 책은 둘 다 적은 비용처럼 묘사. | (a) 관측성 비용 추정 (월 단위 USD) 한 절 추가. (b) "관측성 = IT 비용의 10~15% 흔함" 같은 현실 수치 명시. (c) 카디널리티 / 보존기간 / 샘플링 가이드라인 (예: high-cardinality 라벨 5개 미만) 추가. |
| 02장 §1.2 — "한국어 24/7 기술 지원" | AWS Korea Premier Support 라는 표현. AWS 의 한국어 지원 등급은 Enterprise / Enterprise On-Ramp 부터 한국어 TAM/Sev1 한국어 가능. "Premier" 라는 명칭은 부정확. | "AWS Enterprise Support / Enterprise On-Ramp 등급 이상에서 한국어 24/7 가능" 으로 정정. 시점에 따라 변동되니 "확인 필요" 표시. |
| 02장 §7.1 | "RI / Savings Plan 30~60% 절감" 은 약정 기간(1y/3y) · 결제 옵션(All/Partial/No Upfront) · 인스턴스 종류에 따라 편차가 크다. 본문에 이미 "확인 필요" 가 있어 OK 지만, **Compute Savings Plan vs EC2 Instance Savings Plan vs RI** 의 사용 영역 차이 (EKS Fargate / Lambda 도 Compute SP 적용 가능) 가 빠짐. 이게 실제 절감의 핵심. | "Compute SP 는 Fargate / Lambda 에도 적용 → EKS + Lambda 혼용 환경에 권장" 한 줄 추가. |
| 02장 §4.2 — "CloudFront 만으론 일부 ISP 우회로가 길 수 있음" | 사실 이 부분은 **반대 방향**의 함정도 있다. 국내 CDN(NCP CDN+ / KT CDN) 은 KT/SKB/LGU+ POP 가 풍부하지만 **글로벌 origin 캐시 미스 시 한국→미국→한국** 이 도리어 더 빠를 수 있는 케이스는 라이브 영상 외엔 드물다. 정적 자원은 CloudFront ap-northeast-2 + Seoul Edge 만으로 충분한 케이스가 90%. "멀티 CDN" 권고가 라이브 외 영역까지 일반화될 위험. | "정적 자원 = CloudFront 단일이면 충분 / 라이브 RTMP·HLS 만 멀티 CDN" 으로 영역 분리 명시. |

## 2. 트레이드오프 / 균형 (B)

| 위치 | 발견 | 제안 |
|------|------|------|
| 02장 §2.2 — 단계적 도입 | "3단계: Managed Kubernetes (진짜 필요할 때만)" 까지는 좋다. 그런데 원픽은 "EKS 80 서비스" 로 이미 도입 완료 상태로 등장하고, **EKS 가 정답이라는 톤**으로 8장까지 흐른다. ECS Fargate / App Runner / Cloud Run 옵션이 도입 결정 표 한 줄로만 나오고 트레이드오프 비교가 얕음. 80개 워크로드 중 **상당수는 Fargate / Lambda 로 충분**한데 EKS 에 넣는 게 운영 부채. | "EKS 80 vs Fargate 50 + EKS 30" 같은 혼합 옵션을 트레이드오프 표로. 도메인팀 자율성·SRE 부담의 균형. |
| 02장 §3.2 / case-study §11.1 — Terraform + Atlantis | Atlantis 의 함정이 안 나옴. (1) **prod state 동시 PR 충돌 — Atlantis lock 정책 설계가 어렵다**. (2) PR 이 머지되기 전에 apply 가 먼저 일어나는 워크플로 의 위험 (3) plan/apply 권한 분리, (4) Atlantis 자체의 가용성·시크릿. 게다가 Terraform Cloud / Spacelift / env0 같은 SaaS 대안 비교가 없음. | "Atlantis self-host 운영 부담 vs Terraform Cloud 비용" 비교 한 표. 그리고 **state 분리 전략(환경별 / 도메인별 / 글로벌)** 을 본문 한 절로 분리. 이건 모듈 과다 추상화 함정보다 훨씬 자주 사고남. |
| 02장 §1.3 — 멀티클라우드 | "운영 비용은 곱하기" 는 정확. 그런데 원픽이 그 곱하기를 **이미 한 상태로** 등장한다 (AWS + NCP). "왜 NCP 보조를 결정했는가" 의 트레이드오프가 §8.2 에 3줄 — "비용 협상력·DR·인력 시장". 진짜 비용 (이중 IaC 모듈 / 이중 모니터링 대시보드 / 이중 보안 정책 / NCP 인력 채용 어려움) 은 안 나옴. 실제 NCP/KT 운영 경험자 채용은 AWS 의 1/5 풀. | "멀티 클라우드 인력 비용" 절 추가. 또는 "NCP 결제 이중화" 를 1년 차에 도입하지 말고 **3년차 옵션** 으로 미루는 시나리오를 동등 비중으로 제시. |
| 02장 §6.2 — CI/CD 함정 | "모든 PR 이 prod 자동 배포는 위험" 은 맞다. 그런데 본문 다른 절(§3.4 GitOps) 에선 ArgoCD auto-sync 를 권장. **ArgoCD auto-sync = prod 자동 배포** 가 실질적으로 같은 함수다. 두 절의 메시지가 모순. | ArgoCD 의 sync 모드 (manual / auto / auto + self-heal) 와 environment 단계별(dev auto / stage manual / prod manual+approval) 운영 패턴을 명시. |
| 07장 §10.3 — 에러버짓 90% → 자동 배포 차단 | 이론은 옳다. 실무는 **false positive 폭발**한다. SLI 측정 자체가 한 시간 외부 의존성 장애로 깨지면 90% 소진은 흔함. 그러면 정상 도메인의 배포까지 2주 차단 → 도메인팀이 "에러 버짓 회피용 SLI 조작" 시작 → SRE 신뢰 추락. 이건 SRE 책의 가장 흔한 안티패턴. | "자동 차단 + 1회 manual override (사유 기록)" 룰을 명시. 또는 SLI 깨짐의 원인 분류 (자체 / 외부 의존 / 측정 도구 자체) 를 자동 차단 전 게이트로. |

## 3. 케이스 일관성 (C)

| 위치 | 발견 | 제안 |
|------|------|------|
| case-study §6 결제 SLO 99.99% / RPO 0 vs §11.1 NCP "보조" / §12.1 Q2 "NCP 100% 이중화" | RPO 0 = 동기 복제. AWS Aurora ↔ NCP Cloud DB 간 동기 복제 제품은 **존재하지 않는다** (CDC + 비동기). 따라서 RPO 0 은 "AWS 한 리전 내 멀티 AZ" 까지만 가능. NCP 는 **DR 보조** = RPO 분 단위 비동기. 케이스에 "RPO 0" 과 "NCP 100% 이중화" 가 동시 등장. | RPO 0 을 "AWS 멀티 AZ 동기 복제" 로 명시. NCP 는 "RPO 분 단위 / RTO 5분" 의 콜드/웜 DR. 이게 현실. |
| case-study §10.1 "서비스 약 80개" vs 07장 §10.1 "SRE 8명" vs case-study §11.1 Linkerd + Tempo + Loki 자체 운영 | 위 1번 P1 항목과 동일 구조 — 본문 일관성 차원에서도 어긋남. 1장에서 "팀 30명+ 서비스 추출 결정" 이라더니 8장 결정 요약표에서는 "EKS 80 서비스" 가 자연스럽게 등장. **80개의 서비스가 어떻게 분포되는지** (도메인팀 8개 × 서비스 평균 10개? 모놀리스 1 + 추출 3 + 사이드카 76?) 가 안 나옴. 8개 도메인팀이면 팀당 10 서비스 = 운영 한계 초과. | case-study §11.1 또는 §11.2.1 에 "**80개의 분포**" 표 추가. 모놀리스 1 / 추출 서비스 3 / 배치·워커 / 사이드카 / Cron / 라이브 fanout / BFF 등으로 쪼개야 80 이라는 숫자가 현실적. |
| case-study §11.1 CDN "CloudFront 전체 + NCP CDN+ 라이브" vs 02장 §4.2 "ISP 망 친화도" | 케이스는 라이브 외에는 CloudFront 단일이라 일관 OK. 그런데 02장 §4.2 의 톤이 "CloudFront 만으론 일부 ISP 우회로 길다 → NCP CDN+ / KT CDN 도 후보" 라서 마치 정적 자원도 멀티 CDN 권장처럼 읽힘. 케이스와 본문 톤이 미묘하게 어긋남. | 02장 §4.2 의 권고 범위를 "라이브·대용량 영상" 으로 한정 명시. |
| case-study §2.3 "IT 인프라 비용 매출의 6~8% (연 100~150억)" vs 07장 §10.5 동일 인용 | 매출 1,800억 × 6~8% = 108~144억. 그런데 EKS 80 + RDS Aurora Writer1 Reader3 (2 종류) + MongoDB + OpenSearch + DynamoDB + MSK Kafka + S3 800TB + BigQuery + Flink + Loki/Tempo/Grafana Cloud + Lambda + 멀티 CDN + WAF + NCP DR + GPU 추천. 한국 AWS 가격 기준 감으로 추정해도 이 스택은 **연 200~300억 가깝게 가는 게 보통**. 6~8% 는 글로벌 SaaS 회사 평균이지 **국내 커머스 GMV 대비 IT 비용** 평균이 아님. 국내 커머스는 보통 매출의 10~15% 가 IT (서버 + 인건비 제외 인프라만). | (a) 6~8% 의 출처 / 비교 기준 명시 (인건비 제외? 포함?). ## 6. 종합 한 단락

> 출간될 만한가 / 누구에게 권할 것인가 / 출간 전 반드시 손볼 한 가지

이 책은 **출간될 만하다**. 한국 시장 맥락 위에 트레이드오프 사고를 얹은 입문서로는 국내에 비교 대상이 거의 없다. 다만 인프라/SRE 영역에 한해서는 **"이 책 그대로 따라하면 운영 사고가 난다"** 는 우려가 진심이다. 핵심은 두 가지 — (1) **케이스의 스택 폭이 명시된 인력 풀(SRE 8명)으로는 절대 운영 안 된다**: EKS 80 + Linkerd + Tempo/Loki self-host + Atlantis + 멀티 클라우드 + 결제 99.99% RPO 0 RTO 5분 — 이걸 SRE 8명으로 굴린다는 묘사가 책 전체를 통과한다. 현실은 SRE 12~15명이거나, 스택의 절반을 매니지드(Datadog/Grafana Cloud 통합본/메시 미도입)로 잘라야 한다. (2) **결제 99.99% + RPO 0 + RTO 5분 + AWS↔NCP 이중화**는 1년 안에 달성 불가능한 목표를 "분기별 로드맵 Q2 한 줄"로 가볍게 처리한다. 이건 실제 운영 책임자가 보면 "이 회사 1년 후 결제 사고로 뉴스 난다" 신호다. **추천 독자**는 시니어 백엔드/프론트 → 아키텍트 전환자, 그리고 5~30명 규모 스타트업 CTO/리드. 단, 인프라/SRE 시니어가 동시에 검증하지 않는 환경에서 이 책의 케이스를 "벤치마크" 로 쓰지 말 것을 본문에 명시할 필요가 있다. **출간 전 반드시 손봐야 할 한 가지**는 — 케이스 §11.1 의 인프라 스택과 §4 의 SRE 8명, §6 의 결제 99.99% RPO 0 RTO 5분, §12.1 Q2 로드맵 사이의 **인력·시간·기술적 가능성 일관성 검증**. 이 셋 중 적어도 하나는 현실에 맞게 낮춰야 한다 — 권장은 (a) SRE 12명으로 늘리고 (b) 결제 SLO 를 99.95% / RPO 1분 / RTO 15분으로 현실화하고 (c) 99.99% / RPO 0 / RTO 5분은 "3년 비전" 으로 옮기는 조합. 이 한 가지만 정리되면 나머지 P1·P2 는 다음 판본에서 점진 보완으로 충분하다.
