## 1. 사실 / 정확성 (A)

| 위치 (파일:절 또는 줄) | 발견 | 제안 |
|---------------------|------|------|
| 03-백엔드 §4.2 Outbox SQL 예시 | `INSERT INTO outbox(topic, payload)` 만으로 끝나면, 운영에서는 거의 항상 부족하다. 멱등 키 / aggregate_id / partition_key / occurred_at / trace_id / version 이 빠지면 컨슈머 측 idempotency 와 순서보장(파티셔닝) 이 깨진다. 예시가 그대로 따라하기엔 위험. | `outbox(id, aggregate_type, aggregate_id, event_type, payload, headers, occurred_at, trace_id, partition_key)` 형태로 보강. "왜 이 컬럼이 필요한가" 한 줄씩 설명. |
| 03-백엔드 §4.2 Outbox poller | "별도 프로세스가 outbox 를 읽어 발행" 만 있고, **(a) at-least-once 일 수밖에 없다는 점**, **(b) Debezium CDC 로 outbox 테이블을 직접 tail 하는 변형(가장 운영하기 쉬움)** 이 빠져있다. 실무에선 poller 를 직접 만드는 팀일수록 락·중복 발행·DB 폭주로 고생한다. | 두 변형(application poller vs Debezium-CDC-based outbox)의 트레이드오프 표 추가. MSK 와 Debezium 을 채택했으면 후자가 거의 항상 정답. |
| 03-백엔드 §4.3 Idempotency TTL | "TTL 24시간 정도" 라고 단정. PG/간편결제는 `idempotency_key` 의 의미상 영구(또는 결제 보존 의무 5년) 보존이 안전. 24시간 후 같은 키 재호출 시 새 결제로 처리되면 이중결제 위험. | "결제는 결제 보존 의무 + 분쟁 윈도우 까지", "외부 webhook 수신은 24시간~7일", "내부 명령은 짧게" — 도메인별 TTL 가이드로 분리. |
| 03-백엔드 §4.2 Saga 보상 | 보상 트랜잭션 자체의 실패 처리가 없음. 실무에서 가장 자주 터짐 — 결제 환불 보상이 PG 장애로 실패하면 어떻게 되는가? | "보상의 보상은 없다" 원칙 명시. 보상 실패 시 (1) DLQ + 운영 큐, (2) 사람이 개입하는 manual reconciliation 큐, (3) 일 단위 정합성 reconciler — 이 3계층이 표준. |
| 03-백엔드 §6.1 Kafka 약점 | "운영 복잡" 한 줄. MSK 를 매니지드로 가정한 케이스에서는 컨슈머 lag · rebalance · 파티션 수 변경 불가 · partition skew 같은 **앱 레벨 함정** 이 더 큰 부채. | "Kafka 함정 ≠ 브로커 운영 함정" 박스 추가. partition 수는 사실상 영구 결정 / consumer rebalance 의 stop-the-world / sticky assignor / cooperative rebalance 옵션 정도는 언급. |
| 03-백엔드 §3.3 Read Replica 70% | "읽기 부하의 70% 까지 어렵지 않음" 은 **Aurora 의 reader endpoint 기준** 으로만 맞다. ORM 레벨에서 읽기/쓰기 라우팅 (`@Transactional(readOnly=true)` + `LazyConnectionDataSourceProxy` + Routing DataSource) 의 함정 (트랜잭션 안에서 reader 가 아직 못 본 데이터 — replica lag) 이 빠짐. | "Replica lag 가 사용자 체감으로 노출되는 케이스(주문 직후 내 주문 목록 조회)" 한 단락. read-your-writes 패턴 (방금 쓴 사용자만 writer 로 라우팅) 명시. |
| 03-백엔드 §7.2 토큰 전략 | "Refresh 30일 rotate" 는 모바일에서 실제 운영하면 **로그아웃 무효화·기기 변경·도용 탐지** 가 같이 와야 한다. 단순 rotate 만으로는 탈취된 refresh 가 30일 살아남는다. | refresh family / reuse detection (한 번 쓴 refresh 가 다시 들어오면 family 전체 무효화) 패턴 한 단락 추가. 토스 / 네이버 모바일 사례 일반화. |
| 케이스 §11.2.3 + 03-백엔드 §3 | DB 토폴로지가 Aurora MySQL + Aurora PostgreSQL + MongoDB + DynamoDB + Redis + OpenSearch — **6종**. 220명 조직에서 6종 DB 의 DBA / 백업 / 패치 / 모니터링 / IAM / 감사 비용은 본문에 거의 안 나옴. 케이스 자체가 안티패턴 가까움. | 3장에서 "왜 Mongo 가 필요한가(상품 옵션 다형성)", "왜 PostgreSQL 별도(정산 격리)" 의 **각 결정의 비용** 을 명시. 또는 케이스에서 PostgreSQL 을 Aurora MySQL 의 별도 인스턴스로 통합하는 대안 ADR 을 제시. |
| 03-백엔드 §1.1 헥사고날 패키지 | `port/in`, `port/out` 분리는 "교과서적 헥사고날" 인데, Kotlin Spring Boot 에서 이걸 그대로 적용하면 **인터페이스 폭발** 이 일어난다. 작은 도메인에 `OrderQueryUseCase`, `OrderCommandUseCase`, `OrderRepository` (port/out) + `OrderJpaRepository` (adapter) 5개 파일이 한 도메인당. | "포트 분리는 어댑터가 ≥ 2개일 때 가치" 라는 실무 룰 명시. 단일 어댑터(JPA만 쓸 거면) 인 경우 `Repository` 인터페이스만 두고 adapter 디렉토리 생략하는 절충안 권장. |

## 2. 트레이드오프 / 균형 (B)

| 위치 | 발견 | 제안 |
|------|------|------|
| 03-백엔드 §4 트랜잭션 | Saga 가 "사실상 표준", 2PC 가 "거의 사용 안 함(레거시 외)" 으로 너무 단정적. **국내 결제·정산 영역에서 XA 는 여전히 살아있다** (티맥스 Tibero, 일부 PG, 카드사 인터페이스). 책이 단정적이면 핀테크/결제 분야 독자가 "현실과 다르다" 고 느낀다. | "2PC 가 살아있는 영역(국내 결제 게이트웨이·은행 인터페이스·일부 ERP)" 박스 한 단락. Saga 가 적합한 영역 / XA 가 강제되는 영역의 경계를 그어줄 것. |
| 03-백엔드 §1 도메인 모델 | 도메인 모델 = 헥사고날 으로 거의 직결. **Kotlin Spring Boot 에서의 현실적 함정** (JPA Entity 가 도메인 모델인가 아닌가, MapStruct 의존, Coroutine + JPA 의 비동기 락 함정) 이 빠짐. Java 8년차 시니어가 가장 헷갈리는 지점. | "Entity = 도메인 모델인가" 절 1.4 신설 권장. (a) 같은 객체 (Active Record-ish), (b) 분리 (Persistence Model + Domain Model + Mapper) 의 트레이드오프. |
| 03-백엔드 §2 API | "내부 gRPC" 가 너무 단정적. **Spring Boot 모놀리스 + Go 추출 서비스** 의 케이스에서, Spring 의 grpc-spring-boot-starter 와 Kotlin 의 coroutine-grpc 통합은 운영에서 jar 충돌 / proto 빌드 파이프라인 / Reflection 기반 health check 등 함정이 적지 않다. 작은 조직은 차라리 REST + OpenAPI 가 안정적. | "내부 호출에 gRPC 를 쓰지 않는 합리적 이유" 박스 한 단락. **이미 모놀리스 안에서 끝날 호출까지 gRPC 화하는 안티패턴** 경고. |
| 03-백엔드 §5 캐시 | "로컬 (Caffeine) + 분산 (Redis) 2단" 은 좋은데, **2단의 무효화 전파** (분산 캐시 변경 → 로컬 캐시 invalidate) 가 빠졌다. 실무에서 가장 많이 사고 나는 곳 (한 인스턴스에서 invalidate 한 게 다른 N개 인스턴스에는 전파 안 됨). | (1) Pub/Sub 으로 invalidate 브로드캐스트, (2) 짧은 로컬 TTL (수 초) 로 eventual 수렴, (3) 두 패턴의 트레이드오프 — 한 단락. |
| 03-백엔드 §3 + 케이스 §11.2 | Spring Boot(Kotlin) 가 "도메인 무거운 곳", Go 가 "검색·라이브 게이트" 라는 분담은 합리적. 다만 **추천이 Python 인 부분에서 모노레포 / 빌드 / 배포 / 관측성 표준** 이 분리되는 비용이 책 어디에서도 안 잡힌다. 3개 언어가 곧 3개 표준 라이브러리·3개 SDK·3개 OTel 설정. | 백엔드 §끝 또는 7장에 "다언어 운영의 hidden tax" 절 신설 권장. 220명 조직이 3개 백엔드 언어를 무리 없이 운영하려면 플랫폼팀이 무엇을 표준화해야 하는지(SDK · OTel · 로깅 포맷 · health check · graceful shutdown) 체크리스트. |

## 3. 케이스 일관성 (C)

| 위치 | 발견 | 제안 |
|------|------|------|
| 케이스 §10.1 + 03-백엔드 §8 | "결제 트랜잭션 락이 월 1~2회 주문 처리량을 5분 이상 정체" 가 케이스의 핵심 신호인데, 3장의 §8 시나리오는 "정상 흐름 + PG fallback" 만 보여준다. **이 락이 발생하는 실제 코드 구조** (외부 호출 in-transaction, pessimistic lock on payment row, 재고 차감과 결제의 같은 트랜잭션) 가 안 잡힘. | §8.5 또는 §4.1 에 "원픽이 겪는 실제 락 시나리오" 한 단락. 보통 (a) 외부 PG 호출이 트랜잭션 안, (b) `SELECT ... FOR UPDATE` 가 결제 row 에, (c) 재시도 로직이 락 잡은 채로 sleep — 이 셋 중 하나. 8장에서도 "Q1 안정화" 의 구체 액션으로 이걸 명시하면 케이스가 살아난다. |
| 케이스 §6 SLA + 3장 §4 | 결제 RPO=0, RTO=5분, 가용성 99.99% 가 케이스의 단일 출처. **하지만 3장 어디에서도 RPO=0 을 어떻게 달성하는지** (synchronous replication, multi-region active-active, 결제 로그 별도 영구화) 가 안 나온다. 8장 §4.1 시퀀스에서도 RPO=0 보장 메커니즘이 안 보임. | 3장 §4 끝부분에 "RPO=0 의 현실적 비용" 박스 신설. Aurora Global DB 의 sync vs async, NCP 보조 클라우드와의 sync replication 가능성, 결제 로그를 S3 + Glacier 로 별도 영구화 — 셋 중 하나의 선택을 ADR 로 권장. |
| 케이스 §5.2 "오버셀 0건" + 3장 §4 | 케이스는 "오버셀 0건" 을 강한 제약으로 둠. 3장 §4 어디에도 **재고 차감의 동시성 제어** (Redis INCRBY 기반, Lua script atomic, DB row lock, queued reservation) 가 안 나옴. 선착순 200+ TPS 라는 케이스 §2.1 수치와 직결되는 핵심 패턴인데 누락. | 3장에 "재고/티켓팅 패턴" 미니 절 신설(반 페이지). Redis 기반 atomic decrement + 비동기 DB 영속화 + 보상 reconciliation 의 표준 패턴. 라이브커머스 200+ TPS 가 이 패턴 없이는 안 됨. |
| 8장 §4.1 시퀀스 | 시퀀스에서 "Mono → Pay → Mono" 가 동기 호출 체인. 케이스 §11.2.1 에 따르면 결제는 **모놀리스 안의 도메인** (아직 추출 전, Q2 에 추출 예정). 그렇다면 같은 프로세스 안에서 호출이 일어나야 함. 시퀀스가 마치 별도 서비스 인 것처럼 그려져 있어 혼란. | 시퀀스에 "Q1 시점(현재): 모놀리스 내부 호출 / Q2 이후: gRPC 호출" 두 버전을 병기하거나, 현재 시점만 그리되 주석으로 명시. |
| 03-백엔드 §8.4 + 케이스 §11.2.4 | 8.4 시퀀스에서 outbox poller 가 등장하지만, **outbox 테이블의 위치** (Aurora MySQL 안인지, 별도 DB 인지) 가 모호. 케이스 §11.2.3 에 "회원·주문·결제·... Aurora MySQL" 이라 같은 DB 안에 있다고 추론은 가능하나, Q2 에 결제가 분리되면 outbox 도 분리되어야 함 — 마이그레이션 비용이 큰 항목. | 8.4 또는 8장 §5(로드맵) 에 "결제 분리 시 outbox 도 함께 분리되어야 한다 — 결제 트랜잭션과 outbox 가 같은 DB 트랜잭션 안에 있어야 원자성 유지" 명시. |

## 4. 독자 입장 — 너무 추상 / 너무 세부 / 누락 / 사족 (D)

| 03-백엔드 §6.3 명령 vs 이벤트 | "이벤트 vs 명령" 정의는 좋지만, Kafka 토픽 네이밍 / 스키마 진화(Avro/Protobuf + Schema Registry) / Kafka Streams 또는 Flink 와의 경계 — 운영 시 가장 자주 묻는 질문이 빠짐. | "이벤트 스키마의 진화" 미니 단락 신설. backward / forward compatible 룰, Schema Registry 가 강제하는 것 / 안 하는 것. |
| 03-백엔드 §7 인증 | RBAC vs ABAC vs OPA 가 한 표. **셀러 어드민** (입점 셀러가 자기 상품·주문만 봐야 함) 이라는 케이스의 핵심 인가 시나리오가 빠져있어 추상적. | "셀러 어드민에서 본 ABAC" 한 단락. seller_id 가 모든 쿼리에 강제 주입되는 패턴 (Hibernate Filter / MyBatis interceptor / JPA `@Filter`). 6장의 RLS 와 어떻게 분담되는가. |

## 5. 잘 된 점 (3개 이내)

1. **트레이드오프 표 형식의 일관성** — Saga vs 2PC, 단일 DB vs 도메인별 DB, REST vs GraphQL, Lake vs Warehouse — 모두 같은 표 형식. 시니어 독자가 빠르게 자기 환경에 매핑할 수 있다. 이 책의 가장 큰 강점.
2. **"단일 DB 로 시작" 의 일관된 톤** — §3.2 "분리는 명확한 신호가 올 때" + §3 신호 3가지(스키마 변경 충돌, 부하 점유, 데이터 증가 속도 차이). 이 정도 신호 기반 의사결정 가이드는 한국어 백엔드 책에서 흔치 않다.
3. **케이스 단일 출처 원칙(ADR-0008)** — §11.2 의 스택을 본문에서 인용하는 방식이 정착되어 있어, 챕터 간 모순이 거의 안 보인다. 책 자체의 메타 결정으로서 모범적.

## 6. 종합 한 단락

이 책은 **출간될 만하다**. 한국 시장의 구체적 무대 위에서 트레이드오프 사고를 일관되게 가르치는 한국어 책이 거의 없고, 케이스 단일 출처 / ADR / 다이어그램 표준이 잘 잡혀있다. **가장 권하고 싶은 독자는 모놀리스 운영 3~5년차에서 모듈러 모놀리스 또는 부분 추출 MSA 의사결정을 앞둔 시니어 백엔드 / 리드급** 이다 — 자기 환경의 신호를 어떻게 읽고 어떤 단계까지만 갈지 판단하는 골격을 얻을 수 있다. 다만 백엔드 장 한정으로 보면 **출간 전 반드시 손봐야 할 한 가지는 "운영 관측성과 보상의 보상" 절의 추가** 다. Saga·Outbox·Idempotency 를 책에 쓴 그대로 따라한 백엔드는 6개월 후 (a) outbox lag 메트릭이 없어 이벤트가 1시간씩 늦게 발행되는 걸 모르고, (b) 보상 트랜잭션이 실패한 케이스가 매뉴얼 reconciliation 큐로 가지 않아 데이터 정합성이 슬슬 깨지며, (c) order_id 로 grep 이 안 되는 분산 trace 때문에 P1 인시던트 MTTR 이 케이스 목표(30분)의 두세 배가 된다 — 이 셋이 거의 확정적으로 온다. 추가로 "Spring 생태계에서 Node.js BFF 를 두는 결정의 인력 비용" 과 "DB 6종 운영의 현실 비용" 두 ADR 을 케이스에 추가하면, 이 책이 단지 "잘 정리된 입문서" 를 넘어 **운영 부채를 미리 끊어주는 책** 이 된다.
