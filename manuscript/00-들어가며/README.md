# 0장. 들어가며

> 이 책은 "어떻게 코딩하는가" 가 아니라 "어떻게 결정하는가" 에 대한 책이다.

## 이 장에서 답하는 질문

- 이 책은 누구를 위한 책인가?
- 왜 "한국 시장 한정" 이라는 단서를 강조하는가?
- 책을 어떻게 읽어야 가장 효과적인가?
- 이 책이 다루지 않는 것은 무엇인가?

## 들어가며

대한민국에서 서비스를 만든다는 것은 단지 좋은 코드를 쓰는 일이 아니다.
망분리 규제, PASS 인증, 카카오·네이버 간편로그인, PG 다중화, 명절 트래픽 폭주, 부족한 GPU 코타 — 이 환경에서는 "글로벌 베스트 프랙티스" 가 그대로 들어맞지 않는다.

그렇다고 한국 시장에 갇힌 책을 쓰려는 것은 아니다.
보편적인 아키텍트의 사고법(트레이드오프 분석, 비기능 요구사항 식별, 의사결정 기록)을 한국 환경이라는 구체적 무대에 올려두면, 두 영역 모두 더 잘 보인다.

## 1. 이 책의 독자

이 책은 다음 독자를 일차로 가정한다.

- **시니어 백엔드/프론트엔드 개발자** — 한 영역에선 깊지만, 서비스 전체 그림을 그려야 할 때 길이 흐릿한 사람
- **스타트업 CTO·리드 개발자** — 모든 결정을 혼자 내려야 하는 위치
- **클라우드/인프라 엔지니어** — 애플리케이션 영역까지 시야를 넓히려는 사람

다음은 이차 독자다.

- **주니어 개발자** — 단지 따라하기보다, 시니어가 어떻게 결정하는지 엿보고 싶은 사람
- **PM·기획자** — 엔지니어와 더 정확하게 대화하기 위해

### 전제 지식

한 가지 이상의 언어로 3년 이상 실무 경험이 있다고 가정한다.
기초 문법, 첫 HTTP 요청, REST 입문은 다루지 않는다.

## 2. 이 책의 가설

좋은 아키텍트는 "정답을 안다" 가 아니라 "트레이드오프를 안다" 는 사람이다.

이 가설을 따라 책 전체는 다음 형식을 반복한다.

1. 어떤 영역의 **문제**를 정의한다.
2. 가능한 **선택지** 를 펼친다.
3. 각 선택지의 **장단점·적합한 상황** 을 비교한다.
4. **케이스 스터디**(원픽) 에서 어떤 선택을 했는지, 왜 그렇게 했는지 보여준다.
5. 독자가 자신의 환경에 가져갈 때 점검할 **체크리스트** 를 둔다.

"정답" 은 거의 등장하지 않는다.
대신 "어떤 상황에서 어떤 답이 더 낫다" 가 등장한다.

## 3. 케이스 스터디 — 원픽(OnePick)

책 전체를 관통하는 가상의 서비스가 있다.
**원픽** — 월 1,000만 MAU 의 종합 커머스다.
직매입과 입점 셀러를 함께 운영하고, 라이브커머스를 진행한다.

상세 설정은 [케이스 스터디 문서](../case-study/README.md) 에 따로 있다.
모든 챕터는 마지막에 "원픽에 적용한다면" 절을 두어 추상적 설명을 구체적 예제로 내려놓는다.

원픽은 실존하는 회사가 아니다.
다만 국내 시장의 평균적 모습을 의도적으로 합성했다.

## 4. 책의 구성

책은 세 부분으로 묶인다.

### 1부 — 사고의 틀 (1장)
- 아키텍처라는 일이 무엇인지, 의사결정을 어떻게 기록하는지

### 2부 — 영역별 설계 (2~7장)
- 클라우드 / 백엔드 / 프론트엔드 / 데이터·AI / 보안·컴플라이언스 / 운영·조직

### 3부 — 종합 (8장)
- 1~7장의 결정을 원픽에 한꺼번에 적용. 책 전체의 회수.

## 6. 이 책이 다루지 않는 것

분량과 깊이의 트레이드오프를 위해 의도적으로 제외했다.

- **글로벌 다국가 운영** — 한국 단일 시장 가정
- **B2B / 도매·SaaS 전용 도메인** — 케이스가 B2C 종합몰
- **자체 PG·결제망 운영** — 외부 PG 위탁 전제
- **암호자산·블록체인**
- **게임·미디어 산업의 특화 영역** (실시간 매치메이킹 등)
- **기초 프로그래밍 / 입문 가이드**

위 주제는 별도의 책에서 다룰 가치가 있다. 본 책에서는 명확히 제외한다.

모든 코드는 `code-samples/` 디렉토리에 둔다.
